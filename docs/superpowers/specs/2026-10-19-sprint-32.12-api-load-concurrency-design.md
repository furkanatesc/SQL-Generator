# Sprint 32.12 — API Load / Concurrency Testing (Design)

Phase 13 · Branch `feat/32.12-api-load-concurrency` · Önceki: 32.0–32.11. Phase 13'ün son sprint'i.

## 1. Problem & karar

API'nin eşzamanlı yük altındaki davranışı hiç ölçülmedi. Tek eşzamanlılık testi `test_job_worker.py::
test_concurrent_claims_never_share_a_job`. Kod taraması şu riskleri gösterdi:

- **App DB (`app/database.py::get_db_connection`)**: her çağrıda yeni `sqlite3.connect`, **WAL yok, `busy_timeout` yok**
  (varsayılan 5 sn timeout, rollback-journal). API threadpool'u + worker process aynı dosyaya yazıyor; okuyucular
  commit sırasında yazarı bekliyor, uzun yazma `database is locked` → 500 üretebilir. (Trace DB zaten WAL +
  `busy_timeout=5000` + tek bağlantı/RLock.)
- **`CircuitBreaker.record_failure/record_success`** (`app/llm/failover.py`): sözlük kilitli ama sayaç `+=`
  kilitsiz — eşzamanlı hatalarda sayım kaybolabilir (devre geç açılır).
- **`stream_job_logs` (async)**: `get_job` (senkron SQLite) doğrudan event loop'ta çağrılıyor (inline mod yolunda
  iki yerde) — tüm async istekleri kısa süre bloklar. Worker modu yolu zaten `asyncio.to_thread` kullanıyor.
- Rate limiter, LLM limiter, şema cache kilitli (doğrulanacak, değiştirilmeyecek).

**Karar (kapsam):**
1. **Düzeltmeler (testle kanıtlanmış):**
   - `get_db_connection`: `timeout` + `PRAGMA busy_timeout` (yeni ayar `NL2SQL_DB_BUSY_TIMEOUT_MS`, varsayılan 5000)
     ve `init_db`'de `PRAGMA journal_mode=WAL` (kalıcı dosya ayarı; 32.8 backup online backup API'si WAL ile
     uyumlu — mevcut testi var). Ayar config contract'a + env-contract'a eklenir.
   - `CircuitBreaker` kendi `threading.Lock`'u ile sayaç/durum geçişleri.
   - `stream_job_logs` içindeki senkron `get_job` çağrıları `asyncio.to_thread`.
2. **Süreç-içi eşzamanlılık testleri** (`backend/tests/test_api_concurrency.py`, pytest, thread havuzu +
   `TestClient`, deterministik, LLM yok):
   - N paralel job oluşturma + paralel okuma (`/api/jobs`, `/api/jobs/{id}`) → hiç 5xx yok, oluşan job sayısı = N,
     tüm id'ler tekil.
   - Paralel `POST /api/v1/workspaces` (benzersiz adlar) + liste → 5xx yok, kayıt sayısı tutarlı; aynı adla
     paralel oluşturmada tam olarak bir başarı (mevcut çakışma semantiği neyse o — test önce okur).
   - Uzun süre tutulan bir yazma transaction'ı varken (ikinci bağlantıda `BEGIN IMMEDIATE`) okuma uç noktaları
     bloklanmadan yanıt verir (WAL kanıtı — bugün RED olmalı ya da pragma kontrat testiyle RED).
   - Rate limiter: limit L, paralel M>L istek → tam olarak L başarı, M−L tane 429 (token sayımı yarışsız).
   - Circuit breaker: paralel K hata → `consecutive_failures == K` ve eşik aşılınca açık.
3. **HTTP yük harness'ı** `backend/loadtest/` (yalnız **stdlib**: `urllib` + `ThreadPoolExecutor` — CI runner'ında
   ve backend imajında ek bağımlılıksız çalışır): `python -m loadtest --base-url … --api-key-file … --scenario mixed
   --concurrency 16 --duration 20 --json out.json --max-error-rate 0 --max-p95-ms 2000`.
   - Senaryolar: `read` (health, ready, `/api/jobs`, `/api/v1/query-history`, `/api/v1/workspaces`), `write`
     (`POST /api/v1/workspaces`, `POST /api/jobs/without-file`), `mixed` (ağırlıklı karışım).
   - Her istek için beklenen durum kodları; beklenmeyen kod / bağlantı hatası = hata. 429 yalnız rate limit açıkken
     beklenen sayılır (bayrak).
   - Rapor: senaryo ve uç nokta başına istek sayısı, hata oranı, throughput, p50/p95/p99/max (ms), durum kodu
     dağılımı; JSON + okunabilir özet; eşik ihlalinde exit 1.
   - Saf kısımlar (yüzdelik, eşik değerlendirme, senaryo seçimi, rapor) birim testli; HTTP katmanı
     `uvicorn`'u test içinde ayrı thread'de başlatan bir entegrasyon testiyle uçtan uca doğrulanır.
4. **CI**: `prod-compose-smoke` job'ında backend, rate limit'leri kapatan `docker-compose.loadtest.yml` overlay'iyle
   yeniden oluşturulur (prod compose'da 300 istek/dk sabit; overlay yalnız CI/ölçüm içindir, prodüksiyonda kullanılmaz)
   ve `mixed` senaryo (concurrency 16, ~20 sn) — kapı:
   **hata oranı 0** (5xx/bağlantı hatası yok) + cömert p95 tavanı (2000 ms; paylaşımlı runner gürültüsü). JSON rapor
   artefakt olarak yüklenir. Sonra worker'ın oluşan job'ları işlediği ve `/ready`'nin fail olmadığı kontrol edilir.
5. **Runbook**: "Load testing" bölümü — harness kullanımı, eşiklerin anlamı, ölçülen temel kapasite notu (CI
   değerleri referans, mutlak SLA değil), tek uvicorn process + SQLite sınırları.

Seçilmeyen:
- (a) Locust/k6 — yeni bağımlılık/araç; stdlib harness CI'da ve imajda doğrudan çalışır, ihtiyaç basit.
- (b) Gerçek LLM ile yük — NIM ~40 RPM kotası ve maliyet; yük testi LLM'siz (job'lar worker'da anahtarsız hızlı
  fail olur, kuyruk/DB yazma yolu yine çalışır).
- (c) App DB'yi Postgres'e taşımak / çoklu uvicorn worker — mimari değişiklik, Phase 14 (SaaS) kapsamı.
- (d) Latency'yi sıkı CI kapısı yapmak — paylaşımlı runner'da kararsız; kapı hata oranı, latency rapor + cömert tavan.

## 2. Verify
RED→GREEN: pragma kontrat testi (`journal_mode=wal`, `busy_timeout` ayarla eşleşir), breaker yarış testi, async
uç noktada `get_job`'un thread'de çalıştığı testi, eşzamanlılık testleri, loadtest birim + uvicorn entegrasyon
testleri, CI workflow kontrat testi (adım var, eşikler, artefakt). Full suite + CI 5/5.

## 3. Out of scope (TECH-DEBT §48)
- Dağıtık/çok makineli yük üretimi, uzun soak testleri, gerçek LLM'li yük.
- Çoklu uvicorn worker / process'ler arası paylaşılan rate-limit ve devre durumu (§42, §46 ile bağlantılı).
- App DB için Postgres / bağlantı havuzu; trace DB tek bağlantısının throughput tavanı yalnız ölçülür.
- SLA/SLO tanımı ve latency regresyon kapısı (baseline karşılaştırması).
