# Sprint 30.5 — Query History API (Design Spec)

**Date:** 2026-09-08
**Phase:** 11 (API / Backend Productization) — sixth sprint
**Branch:** `feat/sprint-30.5-query-history-api` (from `main` `304a696`)
**Predecessor:** 30.4 Query Run API (PR #173).

---

## 1. Purpose & motivation

Phase 11 roadmap: … Query Run → **Query History** → Feedback → … 30.4 gave each connection an append-only `query_runs` ledger. 30.5 adds a **read-only history / analytics surface** over that ledger — cross-connection and cross-workspace, with richer filtering and an aggregate summary — none of which the per-resource `GET /api/v1/query-runs` list provides.

**Scope decision (author-decided under the user's "full authority" directive; documented for veto):** 30.5 is a **read-only view over the existing `query_runs` table** (joined to `connections` for workspace scoping) — **no new table, no writes**. It is value-additive over 30.4's runs list: workspace scoping (via the connection→workspace link), a `created_at` date range, free-text SQL search, and a status-count summary. This keeps `query_runs` the single source of run records and avoids duplicating write paths.

## 2. Scope decisions

1. **Read-only** — `GET` list + `GET` summary. No POST/PATCH/DELETE (history is derived from `query_runs`; runs are created via 30.4).
2. **Value-additive filters** beyond `GET /query-runs`: `workspace_id` (join `connections`), `since`/`until` (ISO `created_at` range), `q` (SQL substring, case-insensitive), plus the existing `connection_id`/`status`.
3. **Light history rows** — id, connection_id, workspace_id, sql, status, row_count, created_at. **No result rows** (the full result stays in `GET /query-runs/{id}`; history is a lightweight index).
4. **Aggregate summary** — `GET /api/v1/query-history/summary` → `{ total, by_status: {recorded, succeeded, failed} }`, honoring the same filters.
5. **Filters, not references** — an unknown `workspace_id`/`connection_id`/`status` yields an empty page / zero counts (no 400); consistent with 30.4's status filter.

## 3. Existing landscape (read, not rebuilt)

- 30.4 `query_runs(id, connection_id, sql, status, row_count, …, created_at)`.
- 30.2 `connections(id, workspace_id, …)` — the join for workspace scoping.
- 30.0 contract (`ApiResponse`, `PageMeta`, `ResponseMeta`, `API_V1_PREFIX`) + 30.1–30.4 patterns (guard `EXPECTED_V1_ROUTES`, snapshot regen, `rowid` ordering, `verify_api_key`).

## 4. Architecture

### 4.1 Repository — read-only over `query_runs` (+ `connections` join)

New `backend/app/query_history_repository.py` (no table; pure reads):
- `list_history(limit, offset, connection_id=None, workspace_id=None, status=None, since=None, until=None, q=None) -> list[dict]` — `SELECT qr.id, qr.connection_id, c.workspace_id, qr.sql, qr.status, qr.row_count, qr.created_at FROM query_runs qr LEFT JOIN connections c ON qr.connection_id = c.id` + parameterized WHERE clauses (`qr.connection_id = ?`, `c.workspace_id = ?`, `qr.status = ?`, `qr.created_at >= ?`, `qr.created_at <= ?`, `qr.sql LIKE ?` with `%q%`), `ORDER BY qr.rowid DESC LIMIT ? OFFSET ?`. All filters optional/composable.
- `count_history(**same filters) -> int` — `SELECT COUNT(*)` with the same JOIN/WHERE.
- `summary(**same filters except limit/offset) -> dict` — `{ "total": int, "by_status": {"recorded": n, "succeeded": n, "failed": n} }` via a `GROUP BY qr.status` query (missing statuses default 0).
- A single private `_where(connection_id, workspace_id, status, since, until, q) -> (clause, params)` helper builds the parameterized WHERE for all three functions (DRY, injection-safe — every value is a bound parameter; only fixed column names are interpolated).

### 4.2 API — `/api/v1/query-history` router

New `backend/app/api/query_history.py`, `verify_api_key`-protected.

**Models:**
- `QueryHistoryEntry{ id, connection_id, workspace_id: Optional[str], sql, status, row_count: Optional[int], created_at }`.
- `QueryHistorySummary{ total: int, by_status: dict[str, int] }`.

**Endpoints** (canonical `ApiResponse`):
- `GET /api/v1/query-history` → 200 `ApiResponse[list[QueryHistoryEntry]]` + `meta.pagination` = `PageMeta{limit, offset, count}`; query params `connection_id?`, `workspace_id?`, `status?`, `since?`, `until?`, `q?`, `limit`(1..200, default 50), `offset`(≥0).
- `GET /api/v1/query-history/summary` → 200 `ApiResponse[QueryHistorySummary]`; same filter params (no limit/offset).

No path-param routes → no route-ordering collision between `""` and `/summary`.

### 4.3 Conformance + snapshots

Guard `EXPECTED_V1_ROUTES` gains the two history routes; snapshots regenerated additively (verified vs main). Protected → no security-allowlist change. No new error code.

### 4.4 What does NOT change

`query_runs`/`connections` tables and 30.4's router are read, not modified. No new table, no writes. Only additive: repository, router (+1 include line), regenerated snapshots, §31.

## 5. Data flow

```
GET /api/v1/query-history?workspace_id=..&status=failed&since=..&q=SELECT
  → verify_api_key
  → query_history_repository.list_history(...)  (query_runs LEFT JOIN connections, parameterized WHERE, rowid DESC)
  → ApiResponse[list[QueryHistoryEntry]] + PageMeta

GET /api/v1/query-history/summary?workspace_id=..
  → query_history_repository.summary(...)  (GROUP BY status)
  → ApiResponse[QueryHistorySummary]  ({total, by_status})
```

## 6. Testing strategy

- **Repository unit tests** (seed `query_runs` + `connections` directly): list all; filter by connection_id / workspace_id (join) / status / since+until / q substring; combined filters; paginate; count matches; summary totals + by_status (incl. zero for absent status); unknown filter → empty/zero.
- **Endpoint tests**: envelope + `X-Request-ID`; each filter via query param; pagination meta; summary shape; empty results for unknown filters; 403 without key.
- **Conformance**: guard covers the two history routes.
- `fastapi` pinned `0.115.12`.

## 7. Deliberately out of scope (→ TECH-DEBT §31)

- **Writes** (history is read-only; runs come from 30.4).
- **Cursor pagination / cross-page `total` in `PageMeta`** — the `/summary` endpoint gives a total instead; the list keeps offset+per-page count.
- **Full result rows in history** (fetch via `GET /query-runs/{id}`).
- **Time-bucketed / grouped-by-connection analytics, latency percentiles** (only total + by_status counts).
- **Workspace/connection existence validation on filters** (unknown → empty, by design).
- **Reconciliation with the legacy `jobs`/`query_traces` NL2SQL history** (30.5 covers the 30.4 `query_runs` ledger only).
