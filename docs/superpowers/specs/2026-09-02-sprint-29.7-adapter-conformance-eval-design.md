# Sprint 29.7 — Adapter Conformance Eval Suite (Design Spec)

**Date:** 2026-09-02
**Phase:** 10 (Real Database Adapter Layer) — **final sprint of Phase 10**
**Branch:** `feat/sprint-29.7-adapter-conformance-eval` (from `main` `3396e78`)
**Predecessor:** 29.6 SQL Server Adapter Contract (PR #167). With 29.6 all four connection dialects (PostgreSQL / Oracle / MySQL / SQL Server) plus the in-repo SQLite reference adapter implement the shared execution contract.

---

## 1. Purpose & motivation

Per the roadmap (`docs/PLANNED-SPRINTS.md`, "Sürekli değerlendirme"): 29.7 exists to **sustain the Sprint 21–25 eval harness so accuracy does not silently regress as new adapters/policies/APIs are added.** Concretely: today each per-dialect execution adapter has its own near-duplicate seeded integration test asserting the same battery (3-table JOIN / composite-FK JOIN / truncation) with per-dialect deltas (identifier case folding, resolver, driver, marker, safe-skip). There is **no single place** that asserts "every registered adapter satisfies the shared `SQLDatabaseExecutionAdapter` contract." A fifth adapter (or a regression in an existing one) that violates the contract would only be caught by whatever ad-hoc test the author happened to copy.

29.7 delivers a **single source of truth for adapter conformance**: a per-dialect profile registry that drives (a) a deterministic, Docker-free contract-conformance core that runs on every CI run, (b) a consolidated parametrized live seeded matrix that replaces the four duplicates, and (c) a lightweight observability report emitter.

**This sprint asserts execution-contract conformance only** — NOT NL2SQL generation accuracy (that is the golden/regression eval harness under `app/eval` + `evals`, already covered by 27.10).

## 2. Scope decisions (locked with the user during brainstorming)

1. **Two layers:** a deterministic (Docker-free) contract-conformance core **plus** a parametrized live seeded matrix. (Matches the established 29.x pattern of shipping both an inert deterministic path and a gated live path.)
2. **Consolidate:** the new conformance module **subsumes** the four duplicate `test_*_execution_adapter_seeded_integration.py` files (and the postgres integration equivalent); the old files are **deleted** (not thin shims) so there is exactly one source. Per-dialect markers are preserved on the parametrized cases so existing CI job slicing (`pytest -m <dialect>`) is unchanged.
3. **pytest + lightweight report emitter:** the conformance signal is binary and pytest-shaped and already fits the existing per-dialect CI jobs — **no new gate CLI**. A separate, informational `report --json` emitter snapshots the capability matrix for observability.
4. **SQLite reference adapter** is included in the deterministic contract-conformance core (it is a registered adapter and must satisfy the ABC) but is **outside** the live seeded connection matrix (it is fixture-based, has no DB connection). (User-approved.)

## 3. Existing landscape (as mapped)

- **Shared contract** — `backend/app/evaluation/multi_database_execution.py`:
  - `SQLDatabaseDialect` = `SQLITE, POSTGRESQL, ORACLE, MYSQL, SQLSERVER`.
  - `SQLExecutionAdapterCapability` = `LOCAL_FIXTURE, CONNECTION_REF, READ_ONLY, EXPLAIN_ONLY`.
  - `SQLExecutionMode` = `READ_ONLY, EXPLAIN_ONLY`.
  - `SQLDatabaseExecutionConfig` (dialect, timeout_seconds=2.0, max_rows=1000, execution_mode, explain_analyze=False).
  - `SQLDatabaseExecutionRequest` (case_id, sql, dialect, fixture_ref XOR connection_ref, config); enforces exactly-one-of fixture/connection and `dialect == config.dialect`.
  - `SQLDatabaseExecutionResult` (version, case_id, dialect, sql, sql_sha256, rows, row_count, truncated, execution_error, duration_ms, warnings); `__post_init__` verifies `sql_sha256 == sha256(sql)` and `row_count == len(rows)`.
  - `SQLDatabaseExecutionAdapter(ABC)`: abstract `dialect` property, `execute(request) -> SQLDatabaseExecutionResult`, `capabilities() -> Tuple[SQLExecutionAdapterCapability, ...]`.
  - `SQLiteDatabaseExecutionAdapter` (fixture-based reference; `LOCAL_FIXTURE + READ_ONLY`).
  - `SQLDatabaseExecutionRouter` (frozen; rejects duplicate dialects; `get_adapter(dialect)`; `execute(request)` dispatches by dialect).
- **Four bridge adapters** (`backend/app/evaluation/{postgres,oracle,mysql,mssql}_execution_adapter.py`) — identical bridge shape: `__init__(self, connection_resolver=resolve_local_docker_connection)`, `dialect` property, `capabilities()`, `execute()` delegating to a lower-level `SQL<Db>AdapterContract`; drivers imported lazily; resolver `None` → graceful empty result (never raise). Capability sets: postgres advertises **and accepts** `EXPLAIN_ONLY`; oracle/mysql/mssql advertise `(CONNECTION_REF, READ_ONLY)` and **reject** `EXPLAIN_ONLY`.
- **Resolvers** (`*_connection_resolver.py`): `resolve_local_docker_connection(env=None) -> Optional[...]`; env-var contracts `POSTGRES_TEST_*` / `ORACLE_TEST_*` (uses `SERVICE`, not `DB`) / `MYSQL_TEST_*` / `MSSQL_TEST_*` (read-only login default `sqlgen_ro`).
- **Duplicate seeded tests** — `backend/tests/evaluation/test_{oracle,mysql,mssql}_execution_adapter_seeded_integration.py` and `test_postgres_execution_adapter_integration.py`: `pytestmark = [integration, <dialect>]`; a `_local_docker_<db>_available()` safe-skip helper (import driver → resolve → open+close a short-timeout connection); a `_request(sql, timeout, max_rows)` builder; three tests (JOIN, composite-FK, truncation); per-dialect case-fold assertions.
- **pytest markers** (`backend/pytest.ini`): `manual_llm, integration, postgres, oracle, mysql, sqlserver`.
- **CI** (`.github/workflows/backend-ci.yml`): `backend-tests` (postgres service, full `pytest -q` + eval/gate chain), `oracle-integration` (`pytest -m oracle`), `mysql-integration` (`pytest -m mysql`), `sqlserver-integration` (`pytest -m sqlserver`).

## 4. Architecture

### 4.1 The unifying abstraction — `AdapterConformanceProfile`

A frozen dataclass, one row per dialect, the **single source of truth**. New module `backend/app/evaluation/adapter_conformance.py`.

```
AdapterConformanceProfile(
    dialect: SQLDatabaseDialect,
    adapter_factory: Callable[[], SQLDatabaseExecutionAdapter],   # builds the bridge adapter (default resolver)
    inert_adapter_factory: Callable[[], SQLDatabaseExecutionAdapter],  # builds adapter with a None-returning resolver (Docker-free)
    resolver: Callable[[Optional[Mapping]], Optional[Any]],       # resolve_local_docker_connection
    driver_module_name: str,                                      # e.g. "pymssql" — for import-time isolation assert
    pytest_marker: str,                                           # "postgres" | "oracle" | "mysql" | "sqlserver"
    expected_capabilities: FrozenSet[SQLExecutionAdapterCapability],
    accepts_explain_only: bool,
    case_fold: CaseFold,                                          # UPPER | LOWER | AS_WRITTEN
    seed_fixture_path: Optional[str],                             # tests/fixtures/<db>/seed.sql; None for sqlite
    is_connection_based: bool,                                    # True for the 4; False for sqlite
)
```

A module-level `CONFORMANCE_PROFILES: Tuple[AdapterConformanceProfile, ...]` registry (sqlite + 4). Helper `profiles_for(*, connection_based: bool | None = None)`. A version constant `SQL_ADAPTER_CONFORMANCE_VERSION = "sql_adapter_conformance_v1"`.

The registry is **import-safe**: no DB driver imported at module import (factories/resolvers are references; drivers load lazily only when an adapter actually connects). This lets the deterministic core and the report emitter run with zero Docker and zero driver installs.

### 4.2 Deterministic contract-conformance core (Docker-free)

Reusable assertion helpers in `adapter_conformance.py` (`assert_contract_conformance(profile) -> list[str]` returning violation messages, plus a pure `contract_conformance_report(profile) -> dict`). The pytest module `backend/tests/evaluation/test_adapter_conformance.py` parametrizes over **all** profiles (incl. sqlite), **no DB marker** (runs in `backend-tests` on every CI run). Asserts, per adapter:

1. `adapter.dialect == profile.dialect`; registering all adapters in one `SQLDatabaseExecutionRouter` succeeds (no duplicate-dialect error) and `get_adapter(dialect)` round-trips.
2. `capabilities()` returns a tuple of valid `SQLExecutionAdapterCapability`, deduplicated, equal to `profile.expected_capabilities`.
3. **Inert no-connection graceful** (connection-based profiles): the `inert_adapter_factory` (resolver → `None`) executes a benign `SELECT` request and returns a well-formed `SQLDatabaseExecutionResult` with `execution_error` set, `rows == ()`, `row_count == 0`, and **does not raise**.
4. **EXPLAIN_ONLY consistency:** an `EXPLAIN_ONLY` request against a non-advertising adapter (oracle/mysql/mssql) is rejected deterministically; postgres's inert adapter accepts the mode (advertises the capability) without raising. **Implementation must first confirm the current rejection mechanism** in the three adapters (raise `SQLMultiDatabaseExecutionContractError` vs. return a result with `execution_error`) by reading the code, then the conformance assertion codifies that actual behavior uniformly across the three. If the three diverge from each other, that divergence is itself a conformance finding to surface (not silently paper over).
5. **Result-contract integrity:** every result an adapter returns satisfies the `SQLDatabaseExecutionResult` invariants (`sql_sha256` matches, `row_count == len(rows)`, `version` set). (Naturally holds via `__post_init__`; asserted to lock the contract at the conformance boundary.)
6. **Driver import-time isolation:** a subprocess imports the adapter module and asserts `profile.driver_module_name` is absent from `sys.modules`. (Consolidates the existing per-adapter isolation subprocess tests into one profile-driven parametrization.)

This layer is the always-on silent-regression guard: adding a non-conforming adapter fails here immediately, no Docker required.

### 4.3 Consolidated live seeded matrix

New module `backend/tests/evaluation/test_adapter_conformance_matrix.py`. Parametrizes over the **four connection-based** profiles via `pytest.param(profile, marks=[pytest.mark.integration, getattr(pytest.mark, profile.pytest_marker)], id=profile.dialect.value)`.

- A profile-driven `_local_docker_available(profile)` safe-skip helper (import `profile.driver_module_name` → call `profile.resolver` → open+close a short-timeout connection), replacing the four hand-written `_local_docker_<db>_available()` helpers.
- A shared `_request(profile, sql, *, timeout, max_rows)` builder (connection_ref = `"local_docker"`, config dialect from profile).
- The three canonical conformance checks, each a parametrized test:
  - `test_three_table_join_returns_named_rows` — customers → orders → order_items; asserts named row keys/values with keys normalized per `profile.case_fold`.
  - `test_composite_fk_join` — product_variants → variant_stock on (product_id, sku).
  - `test_max_rows_truncates` — `max_rows=2` → `row_count == 2`, `truncated is True`.
- Case folding is resolved through a `profile.fold(key)` helper (UPPER/LOWER/AS_WRITTEN) so Oracle's uppercase keys and the others' lowercase keys are one parametrized assertion, not four copies.

**CI slicing preserved (no workflow change needed):**
- `backend-tests` (full `pytest -q`, postgres service up): collects all four params; postgres runs live, the other three safe-skip (no service). Deterministic core (4.2) always runs here.
- `oracle-integration` / `mysql-integration` / `sqlserver-integration` (`pytest -m <dialect>`): collect only their param → run live against their service.

The existing per-dialect CI jobs and services are **unchanged**; only the test file they collect changes (from `test_<db>_..._seeded_integration.py` to the shared matrix module). The four old files are deleted.

### 4.4 Report emitter (observability, no gate)

`python -m app.evaluation.adapter_conformance report [--json] [--output PATH]` (argparse `main`, mirroring `app.eval.run_eval`'s CLI shape). For each profile emits:

```
{
  "version": "sql_adapter_conformance_v1",
  "dialects": [
    {"dialect": "sqlserver",
     "capabilities": ["connection_ref", "read_only"],
     "accepts_explain_only": false,
     "case_fold": "lower",
     "is_connection_based": true,
     "driver": "pymssql",
     "contract_conformance": {"ok": true, "violations": []}}
     // live_matrix status is NOT computed here (that requires Docker) — the report is the
     // Docker-free capability/contract snapshot; live pass/skip is observed via pytest/CI.
    ...
  ]
}
```

Fully deterministic, Docker-free, no driver import. **Not wired into CI as a gate.** Covered by `backend/tests/evaluation/test_adapter_conformance_report.py`: asserts the emitter produces valid, stable JSON with one entry per registered dialect and the expected capability sets.

> Design note: the live-matrix pass/skip is intentionally *not* part of the JSON report, because computing it requires Docker and would make the emitter non-deterministic/environment-dependent. The report is the Docker-free contract+capability snapshot; the live signal lives in pytest/CI. This keeps the emitter a pure, reproducible observability artifact. (If a future sprint wants a combined live+contract report, that is a CI-artifact concern — deferred, §7.)

## 5. Components & boundaries

| Unit | Responsibility | Depends on |
|---|---|---|
| `adapter_conformance.py` — `AdapterConformanceProfile` + `CONFORMANCE_PROFILES` | Single source of truth: the per-dialect facts | the 5 adapters, resolvers, `multi_database_execution` |
| `adapter_conformance.py` — `assert_contract_conformance` / `contract_conformance_report` | Pure deterministic conformance logic (no Docker) | profiles, contract types |
| `adapter_conformance.py` — `main()` report CLI | Emit the observability JSON | `contract_conformance_report` |
| `test_adapter_conformance.py` | Deterministic core, all 5 profiles, no DB marker | `assert_contract_conformance` |
| `test_adapter_conformance_matrix.py` | Live seeded matrix, 4 connection profiles, per-dialect marks | profiles, resolvers, drivers |
| `test_adapter_conformance_report.py` | Report emitter smoke (Docker-free) | `main` / report fn |

Each unit is independently understandable and testable; the profile registry is the one interface they share.

## 6. Testing & verification

- **Deterministic core** runs in `backend-tests` on every CI run (no Docker) across all 5 adapters.
- **Live matrix** runs live per dialect in the existing four CI jobs; safe-skips locally without Docker.
- **Report emitter** smoke test is Docker-free.
- **Consolidation safety:** before deleting the four old files, confirm the parametrized matrix asserts a **superset** of what each deleted file asserted (same three query shapes, same case-fold expectations, same truncation semantics). The deletion is part of the same commit as the new matrix so no coverage gap exists at any commit.
- **Full-suite baseline:** currently 2760 passed / 37 skipped. Expected after 29.7: net skip count roughly unchanged (the four deleted seeded files' skips are replaced by the matrix's skips), plus the new Docker-free deterministic + report tests add passes. Exact numbers recorded at implementation time.
- **`git diff main..HEAD`** on `multi_database_execution.py` expected **empty** (29.7 adds no dialect and changes no contract) — same "contract untouched" invariant every 29.x sprint verified.
- Fastapi pinned to 0.115.12 before the full suite run (project quirk).

## 7. Out of scope → TECH-DEBT §25 (no silent drops)

- **SQLite in the live seeded matrix** — sqlite is fixture-based (no DB connection); it is covered by the deterministic core only. A fixture-backed live battery for sqlite is deferred.
- **Report emitter as a CI artifact / combined live+contract report** — the emitter stays a manual/observability tool; wiring its JSON as an uploaded CI artifact, and folding live pass/skip into the report, are deferred.
- **Conformance as a hard gate** (gate CLI + CI gate step, golden/regression-gate parity) — deferred; conformance is gated by the existing per-dialect pytest jobs, not a dedicated gate CLI.
- **NL2SQL accuracy conformance** — out of scope; this suite is execution-contract conformance only (accuracy is the existing golden/regression harness).
- **EXPLAIN_ONLY parity across dialects** — unchanged; only postgres advertises it. Conformance asserts each adapter's *declared* capability set, not that all dialects support EXPLAIN.
- **Live pipeline / connection registry wiring** — unchanged Phase 10 boundary (→ Phase 11 · 30.x).
