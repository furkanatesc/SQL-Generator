# Sprint 32.3 — Database Migration Strategy (Design)

Phase 13 · Branch `feat/32.3-db-migration-strategy` · Önceki: 32.0 (prod compose, kalıcı volume'lar), 32.2.

## 1. Problem & karar

İki SQLite veritabanı var: uygulama DB'si (`app/database.py::init_db`, `SQLGEN_DB_PATH`, 13 tablo) ve trace DB
(`app/trace/sqlite_store.py::_init_db`, `NL2SQL_TRACE_DB_PATH`). İkisi de her açılışta `CREATE TABLE IF NOT
EXISTS` + ad-hoc `ALTER TABLE ... ADD COLUMN` (try/except ya da `PRAGMA table_info`) ile kuruluyor. Sürüm
kaydı yok: hangi DB hangi şemada bilinmiyor, kolon ekleme dışında bir değişiklik (yeniden adlandırma, veri
dönüşümü, index) güvenle yapılamıyor, eski koda yeni DB verilince fark edilmiyor. 32.0'dan beri veri kalıcı
volume'da yaşadığı için bu artık prod riski (TECH-DEBT §36.5).

**Karar (kapsam):** 32.3 = **hafif, sürümlü, ileri-yönlü migration runner** (`app/migrations/`) + iki DB için
**baseline migration (v1 = bugünkü şema)** + `schema_migrations` sürüm tablosu + **startup/readiness
uyarıları** + **operatör CLI'ı** (`python -m app.migrations status|upgrade`).

Seçilmeyen:
- (a) Alembic — SQLAlchemy'ye bağımlı; proje ham `sqlite3` kullanıyor, SQLAlchemy modeli yok. Yeni ağır
  bağımlılık + autogenerate'in tutmayacağı ham SQL. Runner arayüzü ileride Alembic'e geçişe engel değil.
- (b) Down migration'lar — SQLite'ta DDL geri alma (kolon drop) sınırlı; geri dönüş stratejisi = yedekten
  dönüş (32.8). Runner yalnız ileri.
- (c) Harici DB (Postgres) servisleştirme — ayrı iş (§36.5 kalan kısmı → TECH-DEBT §39).
- (d) Migration öncesi otomatik yedek — 32.8 Backup/Restore kapsamı.

## 2. Design

### 2.1 Runner (`app/migrations/runner.py`)
- `Migration(version: int, name: str, apply: Callable[[sqlite3.Connection], None])`.
- `validate_registry(migrations)`: sürümler 1..N kesintisiz, artan, adlar benzersiz (aksi `ValueError`;
  test registry'leri import'ta doğrular).
- `schema_migrations(version INTEGER PRIMARY KEY, name TEXT NOT NULL, applied_at TEXT NOT NULL)`.
- `inspect(conn, migrations) -> MigrationStatus(current, latest, pending, ahead)` — salt-okur, tablo
  yoksa `current=0`.
- `migrate(conn, migrations) -> MigrationStatus(..., applied, error)`:
  - `current > latest` (**DB koddan yeni**): hiçbir şey uygulanmaz, `ahead=True`.
  - Her bekleyen migration **kendi transaction'ında** (`isolation_level=None` + açık `BEGIN`/`COMMIT`,
    SQLite DDL transaction'lıdır): `apply` + `schema_migrations` satırı birlikte commit; hata → `ROLLBACK`,
    sonraki migration'lar denenmez, `error` = exception sınıf adı (mesaj/SQL değil), loglanır.
  - **Raise etmez** (warn-only startup ilkesi); sonuç startup validation'da kritik uyarı olur.
- `ensure_column(conn, table, column, column_sql)` — `PRAGMA table_info` ile idempotent kolon ekleme
  (baseline'ın eski DB'leri yükseltmesi için).

### 2.2 Registry'ler
- `app/migrations/app_db.py::APP_MIGRATIONS = (v1 "baseline",)` — `init_db`'deki tüm DDL birebir taşınır
  (13 tablo + 6 index + `jobs` için 3 `ensure_column`). Seed'ler (configs, synonym bootstrap) veri olduğu
  için `init_db`'de kalır; `init_db` = `migrate(APP_MIGRATIONS)` + seed.
- `app/migrations/trace_db.py::TRACE_MIGRATIONS = (v1 "baseline",)` — `nl2sql_traces` + 4 `ensure_column` +
  `traces`. `_backfill_metadata_filter_columns` her açılışta çalışmaya devam eder (davranış korunur).
- Mevcut DB'ler: baseline idempotent olduğu için eski bir DB'de v1 sorunsuz uygulanır ve kaydedilir.
- **Kural (docs):** yayınlanmış bir migration asla düzenlenmez; değişiklik = yeni sürüm.

### 2.3 Startup uyarıları (`validate_runtime_config`)
| Kod | Severity | Koşul |
|---|---|---|
| `DB_SCHEMA_AHEAD` | critical | app ya da trace DB sürümü koddaki son sürümden büyük (eski imaj + yeni DB) |
| `DB_MIGRATIONS_PENDING` | critical | açılıştan sonra hâlâ bekleyen migration var (migration başarısız) |

Yalnız DB adı (`app`/`trace`) ve sürüm numaraları; yol yok. Trace DB yoksa (henüz oluşturulmamış) atlanır.

### 2.4 CLI
`python -m app.migrations status` → her iki DB için JSON (`db`, `current`, `latest`, `pending`, `ahead`);
`upgrade` → bekleyenleri uygular, hata/ahead varsa exit 1. Prod: `docker compose exec backend python -m
app.migrations status`.

## 3. Verify
`backend/tests/test_migrations.py`: registry doğrulama; boş DB → v1 + beklenen tablo/kolon kümesi; eski
şemalı DB (eksik `jobs` kolonları / eksik trace kolonları) yükseltilir ve veri korunur; ikinci çalıştırma
no-op; başarısız migration rollback + kayıt yok + sonraki denenmez; ahead → uygulama yok; uyarılar;
CLI exit kodları. Full suite + CI 5/5 (prod-compose-smoke kalıcılık adımı container yeniden yaratımında
migration'ın no-op olduğunu fiilen doğrular).

## 4. Out of scope (TECH-DEBT §39)
- Down migration / otomatik rollback; migration öncesi otomatik yedek (→ 32.8).
- Harici DB (Postgres) / Qdrant servisleştirme, çoklu replika (§36.5).
- Çok-process eşzamanlı migration kilidi (tek backend process varsayımı; SQLite yazma kilidi + idempotent
  baseline riski sınırlar).
- Qdrant collection şema migration'ı (§28.8 notu).
- Migration checksum'ı (yayınlanmış migration'ın düzenlenmesini tespit) — şimdilik doküman kuralı.
