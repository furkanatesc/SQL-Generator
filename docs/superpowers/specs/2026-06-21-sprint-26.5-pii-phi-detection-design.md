# Sprint 26.5 — PII / PHI Detection Contract · Design

**Phase 7 (Security & Governance) · Contract-first, no execution · 2026-06-21**

## 1. Purpose

Define a deterministic, static (no-execution) backend contract that **detects**
whether a query plausibly touches personal data (PII) or protected health
information (PHI), and reports *what kind* and *with what confidence*. Where 26.0
answers "may this run?", 26.1 "right tenant?", 26.2 "is it read-only?", 26.3 "how
risky?", and 26.4 "does it touch a **declared-sensitive** resource (and what to do)?",
26.5 answers:

* Does this query plausibly involve PII/PHI, by **category** (email, SSN, phone,
  credit card, IBAN, date of birth, medical record number, diagnosis, …), and how
  confident is that judgement?

It is a **pure signal / detector — not a gate.** It returns NO
`ALLOW`/`DENY`/`REQUIRES_APPROVAL` decision. This mirrors 26.3 (risk classifier):
the detector produces a typed signal that downstream gates and governance consume —
26.4 (sensitive-data gate), 26.6 (audit), 26.7 (approval). The detector explaining
"PHI present, high confidence" never competes with a gate's decision; it feeds it.

Where 26.4 is **declaration-based** (it enforces only what the operator declared
sensitive), 26.5 is **heuristic**: it infers categories from identifier names and
literal value formats *without* any operator declaration being required. A declared
category map is supported as an optional, sound override — but the value of 26.5 is
catching PII/PHI the operator never declared.

## 2. Scope

**In scope:** the contract — category/data-class/source/confidence enums, an
immutable optional declaration rule, an immutable request/result, a stateless
detector, JSON-safe **secret-free** `to_dict()`, three detection layers (declared
map, identifier-name heuristics, SQL literal-value heuristics incl. Luhn), and
exhaustive unit tests.

**Out of scope (later sprints / deliberate):** any ALLOW/DENY decision (that is
26.4/26.7), audit persistence (26.6), approval orchestration (26.7), prompt-injection
defense (26.8), result-set/row privacy over *returned data* (26.9 — 26.5 sees only
the SQL, never result rows), a real SQL parser, alias/schema resolution, catalog
metadata, locale-specific national-ID validation beyond the chosen formats, any I/O,
DB driver, adapter execution, API/UI, tenant/RBAC/AuthN.

## 3. Module layout

- `backend/app/security/sql_pii_phi_detection.py`
- `backend/tests/security/test_sql_pii_phi_detection.py`
- Exported from `backend/app/security/__init__.py` (mirrors 26.0–26.4).
- Contract version: `sql_pii_phi_detection_contract_v1`.
- Reuses the shared `app.security._sql_text` sanitizer (`to_executable_core`) for the
  **identifier** layer so keywords/identifiers inside string literals or comments are
  never matched. The **literal-value** layer deliberately scans a *different* view of
  the statement (see §7). Performs no I/O.

## 4. Enums

```python
class SQLDataClass(str, Enum):          # the PII vs PHI axis
    PII = "pii"                          # personal data
    PHI = "phi"                          # protected health info (HIPAA-style)

class SQLPiiPhiCategory(str, Enum):
    EMAIL = "email"
    PHONE = "phone"
    SSN = "ssn"                          # US-style national identifier
    CREDIT_CARD = "credit_card"
    IBAN = "iban"
    DATE_OF_BIRTH = "date_of_birth"
    PERSON_NAME = "person_name"
    POSTAL_ADDRESS = "postal_address"
    MEDICAL_RECORD_NUMBER = "medical_record_number"  # PHI
    DIAGNOSIS = "diagnosis"                          # PHI
    HEALTH_GENERIC = "health_generic"                # PHI

class SQLPiiPhiDetectionSource(str, Enum):
    DECLARED = "declared"                # operator-declared map (sound)
    IDENTIFIER_NAME = "identifier_name"  # name heuristic (best-effort)
    LITERAL_VALUE = "literal_value"      # value-format heuristic (best-effort)

class SQLPiiPhiConfidence(str, Enum):    # ordered low -> high
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"

class SQLPiiPhiReasonCode(str, Enum):
    NO_PII_PHI_DETECTED = "no_pii_phi_detected"
    PII_DETECTED = "pii_detected"           # PII only
    PHI_DETECTED = "phi_detected"           # any PHI present (implies highest concern)
    UNUSABLE_INPUT = "unusable_input"

class SQLPiiPhiEvaluatedVia(str, Enum):
    EXPLICIT_REFERENCES = "explicit_references"  # caller-supplied identifier lists (sound view)
    SQL_TEXT = "sql_text"                        # heuristics over the SQL string
    NONE = "none"                                # no usable input
```

A module-level `_CATEGORY_DATA_CLASS: Dict[SQLPiiPhiCategory, SQLDataClass]` maps each
category to PII or PHI. A `_CONFIDENCE_ORDER` map gives `LOW < MEDIUM < HIGH` so the
result can report the **max** confidence deterministically.

> Reason-code precedence: PHI presence dominates — if any matched category is PHI the
> reason code is `PHI_DETECTED` even when PII is also present (PHI is the stricter
> governance signal). PII-only matches → `PII_DETECTED`. No matches → `NO_PII_PHI_DETECTED`.

## 5. Optional declaration rule (trusted config, sound layer)

```python
@dataclass(frozen=True)
class SQLPiiPhiDeclaration:
    resource_id: str                     # normalized lowercase "users.ssn" or "patients.mrn"
    category: SQLPiiPhiCategory
```

- Validated in `__post_init__`: `category` must be a real enum member; `resource_id`
  a non-empty string, normalized to lowercase, and table-qualified (`table.column`,
  must contain a `.`). Declarations are trusted config (same stance as 26.4 rules).
- A declared match on a referenced column yields source `DECLARED` at confidence
  `HIGH` (it is an operator assertion, not a guess). Declarations are optional; an
  empty declaration set is the common case and still detects heuristically.

## 6. Request (hybrid reference source — mirrors 26.4)

```python
@dataclass(frozen=True)
class SQLPiiPhiDetectionRequest:
    version: str
    sql: Optional[str] = None
    referenced_tables: Optional[Sequence[str]] = None
    referenced_columns: Optional[Sequence[str]] = None
    dialect: str = "generic"
```

- `version` mismatch → raises `SQLPiiPhiDetectionContractError` (contract violation).
  `dialect` must be a non-empty string (raises). All *other* malformed input
  (non-string `sql`, empty everything) yields a fail-closed **result**, never a raise
  (mirrors 26.4 / 26.3).
- **Identifier source resolution (hybrid):**
  1. If `referenced_tables`/`referenced_columns` provided → use them verbatim
     (normalized lowercase) for the identifier-name + declared layers. This is the
     **sound identifier view** → `evaluated_via = EXPLICIT_REFERENCES`.
  2. Else if `sql` is a non-empty string → identifiers come from best-effort
     extraction over `to_executable_core(sql)` → `evaluated_via = SQL_TEXT`.
  3. Else → no usable input.
- **Literal-value layer** runs whenever `sql` is a usable string, *independently* of
  which identifier source was chosen (it needs the raw literals; see §7). So a caller
  who supplies both explicit refs *and* `sql` gets `evaluated_via = EXPLICIT_REFERENCES`
  for the identifier view **and** literal scanning over the SQL. `evaluated_via`
  describes the identifier view only; literal scanning is reported per-match via the
  `LITERAL_VALUE` source.

## 7. The three detection layers

**Layer A — Declared map (sound, confidence HIGH, source `DECLARED`).** For each
referenced column present in the declaration set, emit a match with the declared
category. Only runs on referenced columns (explicit or extracted).

**Layer B — Identifier-name heuristics (best-effort, source `IDENTIFIER_NAME`).**
Match referenced table/column/identifier *names* against per-category name patterns
over the executable core (literal-free). Examples (case-insensitive, word-ish
boundaries): `ssn|social_security` → SSN; `email|e_mail` → EMAIL;
`phone|mobile|msisdn` → PHONE; `dob|birth_date|date_of_birth|birthday` → DATE_OF_BIRTH;
`iban` → IBAN; `card_number|cc_number|credit_card` → CREDIT_CARD;
`first_name|last_name|full_name|surname` → PERSON_NAME; `address|street|postcode|zip`
→ POSTAL_ADDRESS; `mrn|medical_record` → MEDICAL_RECORD_NUMBER; `diagnosis|icd`
→ DIAGNOSIS; `patient|disease|treatment|prescription` → HEALTH_GENERIC. Confidence
`MEDIUM` (a name match is a strong but not certain signal). Matches carry the matched
identifier (a schema name the operator exposed — not a value) for audit.

**Layer C — SQL literal-value heuristics (best-effort, source `LITERAL_VALUE`).**
Scan the **raw SQL string** for value formats: email regex, US SSN
(`\d{3}-\d{2}-\d{4}`), credit-card-like digit runs **gated by the Luhn checksum**
(only Luhn-valid → emit, raising confidence), IBAN format, E.164/long phone numbers.
Confidence: Luhn-valid card → `HIGH`; well-anchored email/SSN/IBAN → `MEDIUM`; looser
phone/number → `LOW`. **Secret-free:** a literal match records only the category,
source, and confidence — **never** the matched value, offset, or a snippet. The
matched-identifier field is `None` for literal matches.

> Why Layer C scans raw SQL, not the sanitized core: `_sql_text.sanitize` masks string
> literals by design (it answers "what is executable code"). PII leaked into a
> `WHERE ssn = '123-45-6789'` lives *inside* a literal, so Layer C must look at the
> unmasked text. Trade-off (documented limitation): regexes may also match inside
> comments — an over-detection bias, acceptable and even desirable for a *signal*
> (never a gate). We still never store the offending text, so no secret leaks.

## 8. Detection flow

1. Validate request type & version (mismatch raises).
2. Compute `sql_sha256` when `sql` is a non-empty string (else `None`).
3. Resolve identifier source (§6). Determine `evaluated_via`.
4. If `evaluated_via == NONE` **and** no usable `sql` for Layer C → return
   `NO matches`, `reason_code = UNUSABLE_INPUT`, empty categories, `has_phi = False`,
   `highest_confidence = None`. (Detector cannot assert presence *or* absence, so it
   reports "could not evaluate" rather than a false "clean".)
5. Run Layer A (declared), Layer B (identifier names) over the resolved identifiers;
   run Layer C (literals) over raw `sql` when usable.
6. Aggregate:
   - `detected` = de-duplicated, deterministically ordered tuple of matches.
   - `categories` = matched categories, de-duplicated and sorted into a tuple (§9).
   - `has_phi` = any matched category maps to `PHI`.
   - `highest_confidence` = max confidence among matches (`None` if no matches).
   - `reason_code` per §4 precedence (PHI > PII > none).
7. Build immutable result.

## 9. Result (immutable, audit-grade, secret-free)

```python
@dataclass(frozen=True)
class SQLPiiPhiMatch:
    category: SQLPiiPhiCategory
    data_class: SQLDataClass
    source: SQLPiiPhiDetectionSource
    confidence: SQLPiiPhiConfidence
    identifier: Optional[str]      # schema name for name/declared matches; None for literals
    def to_dict(self) -> Dict[str, Any]: ...

@dataclass(frozen=True)
class SQLPiiPhiDetectionResult:
    version: str
    detected: Tuple[SQLPiiPhiMatch, ...]
    categories: Tuple[SQLPiiPhiCategory, ...]   # sorted, de-duplicated
    has_phi: bool
    highest_confidence: Optional[SQLPiiPhiConfidence]
    reason_code: SQLPiiPhiReasonCode
    reason: str
    sql_sha256: Optional[str]
    evaluated_via: SQLPiiPhiEvaluatedVia
    dialect: str
    def to_dict(self) -> Dict[str, Any]: ...     # JSON-safe; enum .value's; no raw SQL/values
```

- Carries **no raw SQL and no matched values** — only `sql_sha256` (when sql given),
  categories, and matched *identifier names* (schema metadata the operator exposed,
  not secrets). Literal matches carry no identifier and no value.
- `detected` is de-duplicated on `(category, source, identifier)` and ordered
  deterministically: data_class (PHI before PII), then category value, then source,
  then confidence desc, then identifier (`None` last).

## 10. Documented limitations (26.3/26.4-style honesty)

- **Heuristic, both directions:** name/value patterns under-detect (a `notes` column
  full of PHI, an unlisted national-ID format) *and* over-detect (a `comment` column,
  a non-PII number that passes Luhn by chance, PII-looking text inside a SQL comment).
  It is a **signal, never proof**, and never a gate.
- Identifier extraction shares 26.4's blindness: alias-blind, nesting-blind,
  schema-qualification-blind. **Sound identifier usage = explicit references.**
- Layer C is locale-limited to the chosen formats (US SSN, generic IBAN/email/phone,
  Luhn cards); other national IDs are out of scope this sprint.
- A real fix for soundness (parser + catalog + data-classification metadata, and/or
  value sampling under execution) is later-sprint work; 26.5 is explicitly MVP.

## 11. Test matrix

- No declarations, benign query (`SELECT id FROM orders`) → `NO_PII_PHI_DETECTED`,
  empty, `has_phi = False`, `highest_confidence = None`.
- Declared map: referenced declared column → `DECLARED`/`HIGH` match, right category.
- Identifier-name layer: each category's name pattern matches (table & column names),
  via explicit refs and via SQL extraction.
- Literal layer: email, SSN, IBAN, phone literals in `WHERE`/`VALUES` detected;
  Luhn-valid card → `CREDIT_CARD`/`HIGH`; Luhn-invalid digit run → not a card.
- PHI categories (MRN/diagnosis/health_generic) → `has_phi = True`,
  `reason_code = PHI_DETECTED` even when PII also present.
- PII-only → `reason_code = PII_DETECTED`.
- `evaluated_via` correctness: explicit refs → `EXPLICIT_REFERENCES`; sql-only →
  `SQL_TEXT`; neither → `NONE`. Explicit refs **plus** sql → `EXPLICIT_REFERENCES`
  for identifiers yet literal matches still emitted from the sql.
- Unusable input (no refs, no sql / non-string sql / empty sql) → `UNUSABLE_INPUT`,
  empty detected, `evaluated_via = NONE`.
- Version mismatch (request & result) → raises.
- Declaration validation: bad enum, empty/unqualified `resource_id` → raises.
- Immutability (`FrozenInstanceError`); `detected` de-dup & deterministic order;
  `categories` sorted & de-duplicated; `highest_confidence` = true max.
- Secret-free: `to_dict()` JSON-serializable, contains no raw SQL and no matched
  literal value (assert a known-secret SSN/card string is absent from the dict).
- Case-insensitivity of name + declared matching.
