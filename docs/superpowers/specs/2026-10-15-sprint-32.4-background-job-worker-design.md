# Sprint 32.4 — Background Job Worker (Design)

Phase 13 · Branch `feat/32.4-background-job-worker` · Önceki: 32.3 (sürümlü migration'lar).

## 1. Problem & karar

NL→SQL job'ları (`POST /api/files/upload`, `POST /api/jobs/without-file`) API process'inde FastAPI
`BackgroundTasks` ile çalışıyor (`main.py::process_job_pipeline`). Sonuçlar:
- API restart/crash'inde `pending`/`processing` job'lar **sonsuza kadar** o durumda kalır (yetim).
- Uzun LLM çağrıları API worker thread'lerini işgal eder; job yürütme API'den ayrı ölçeklenemez.
- Job logları yalnız process belleğinde (`job_logs_cache`, `job_queues`); restart'ta kaybolur, başka
  process'ten SSE ile izlenemez.

**Karar (kapsam):** 32.4 = **DB-tabanlı claim modeliyle çalışan ayrı worker process** + **kalıcı job logları**
+ **yetim/stale job kurtarma** + **prod compose'ta `worker` servisi**. Yürütme modu ayarla seçilir:
`NL2SQL_JOB_EXECUTION_MODE=inline` (varsayılan; bugünkü davranış, dev/test) | `worker` (API yalnız
`pending` job yazar, worker claim edip çalıştırır; prod compose bunu sabitler).

Seçilmeyen:
- (a) Celery/RQ + Redis — yeni altyapı servisi + bağımlılık; 32.5 Queue System bunu (öncelik, retry,
  backoff, dead-letter, eşzamanlılık limiti, harici broker) değerlendirecek. 32.4'ün `jobs` tablosu claim
  modeli broker'sız, tek-host SQLite ile çalışır.
- (b) API içinde gömülü worker thread'i — yalnız restart yetimliğini çözer, izolasyon/ölçekleme yok.
- (c) Stale job'u otomatik yeniden kuyruğa almak — LLM maliyeti + idempotency belirsiz; retry politikası
  32.5'te. 32.4 stale job'u `failed` yapar (mesajla).

## 2. Design

### 2.1 Şema (APP_MIGRATIONS v2 `job_worker`)
- `jobs`: `worker_id TEXT`, `claimed_at TEXT`, `heartbeat_at TEXT` (ensure_column).
- `job_logs(id INTEGER PK AUTOINCREMENT, job_id TEXT NOT NULL, step INTEGER, message TEXT NOT NULL,
  created_at TEXT NOT NULL)` + `idx_job_logs_job_id`.
- Runner iyileştirmesi: migration transaction'ı `BEGIN IMMEDIATE` + transaction içinde sürüm yeniden
  kontrolü → backend ile worker aynı anda açılırsa ikinci process migration'ı atlar (§39.3 tek-host için).

### 2.2 `app/jobs/repository.py`
- `claim_next_job(worker_id) -> dict | None`: `BEGIN IMMEDIATE`, en eski `pending` (created_at, rowid),
  `status='processing'`, `worker_id`, `claimed_at`, `heartbeat_at` = şimdi. Atomik; iki worker aynı job'u alamaz.
- `touch_heartbeat(job_id, worker_id)`.
- `fail_abandoned_jobs(statuses, older_than_seconds=None) -> list[str]`: belirtilen durumdaki (ve
  `COALESCE(heartbeat_at, updated_at)` eşikten eski) job'ları `failed` + açıklayıcı `error_message` yapar.
- `append_job_log(job_id, message, step)`, `list_job_logs(job_id, after_id=0)`.

### 2.3 `app/jobs/executor.py::execute_job(job_id, request_id=None, on_log=None)`
`process_job_pipeline` gövdesi birebir taşınır (late-bound `app.database` / `app.sql_pipeline` lookup'ları
korunur — mevcut testler bunları patch'liyor); her log satırı `job_logs`'a da yazılır. `main.process_job_pipeline`
ince sarmalayıcı: in-memory cache + SSE kuyrukları + EOF (inline davranışı aynen).

### 2.4 `app/jobs/worker.py` (`python -m app.jobs.worker`)
- `JobWorker(worker_id, poll_seconds, stale_seconds)`: `run_once()` → stale kurtarma + claim + yürütme
  (yürütme sırasında heartbeat thread'i, aralık `max(1, stale/5)` sn); `run_forever(stop_event)`; SIGTERM/SIGINT
  → mevcut job bittikten sonra çıkış.
- Açılışta `init_db()` (migration'lar). Her döngüde liveness dosyası (`<tmp>/sqlgen_worker_alive`);
  `python -m app.jobs.worker healthcheck` dosya ≤ 60 sn ise 0.
- Eşzamanlılık: process başına 1 job; ölçekleme = daha çok worker container (claim atomik).

### 2.5 API
- Job oluşturan iki endpoint: `inline` → `BackgroundTasks` (bugünkü); `worker` → yalnız `pending` kayıt.
- SSE `/api/jobs/{id}/stream`: `worker` modunda `job_logs` tablosundan 1 sn poll (terminal durumda biter);
  `inline` modunda bugünkü in-memory akış.
- Startup (`inline`): `pending`/`processing` kalan job'lar yetimdir → `failed` ("interrupted by restart").
  `worker` modunda API kurtarma yapmaz (worker heartbeat'e göre yapar).
- Startup uyarısı `JOB_QUEUE_STALLED` (warning): `worker` modunda `stale_seconds`'tan eski `pending` job var
  (worker çalışmıyor olabilir).

### 2.6 Ayarlar (Settings + 32.1 sözleşmesi)
`NL2SQL_JOB_EXECUTION_MODE` (`inline`|`worker`, default `inline`), `NL2SQL_JOB_WORKER_POLL_SECONDS` (1.0),
`NL2SQL_JOB_STALE_SECONDS` (300).

### 2.7 Prod compose
Yeni `worker` servisi: aynı backend imajı, `command: python -m app.jobs.worker`, `sqlgen_data` +
`sqlgen_uploads` volume'ları (Qdrant yok — pipeline kullanmıyor; gömülü Qdrant tek-process kilitli),
pinned env (environment, DB/trace/upload yolları, `NL2SQL_JOB_EXECUTION_MODE=worker`, opsiyonel
`NVIDIA_API_KEY`), healthcheck, `depends_on: backend: service_healthy`. Backend `NL2SQL_JOB_EXECUTION_MODE=worker`.
CI smoke: NVIDIA key yokken job'u worker claim eder ve `failed` yapar (API değil, worker'ın yürüttüğünün
kanıtı: `worker_id` dolu) ve log satırı `job_logs`'tan SSE ile okunur.

## 3. Verify
`backend/tests/test_job_worker.py`: migration v2 (eski v1 DB'yi yükseltir), claim atomikliği/sırası,
heartbeat, stale kurtarma, executor log kalıcılığı, worker `run_once` (başarı/başarısız/iptal), mod
bazlı endpoint davranışı, SSE DB-replay, inline startup kurtarma, `JOB_QUEUE_STALLED`, healthcheck,
runner `BEGIN IMMEDIATE` yeniden kontrolü. Mevcut job/pipeline testleri değişmeden geçer. Full suite + CI 5/5.

## 4. Out of scope (TECH-DEBT §40)
- Retry/backoff, öncelik, dead-letter, eşzamanlılık limiti, harici broker (→ 32.5 Queue System).
- `job_logs` retention/temizleme; job iptalinin çalışan LLM çağrısını kesmemesi (yalnız sonuç yazılmaz — bugünkü gibi).
- Stale job için taksonomi `error_code` (ör. `JOB_ABANDONED`) — frontend `errorInfo.ts` aynası gerektirir.
- Worker'ın Qdrant/RAG kullanan işleri çalıştırması (gömülü Qdrant çok-process'te kilitli).
- Çok-host worker (SQLite paylaşımı tek-host).
