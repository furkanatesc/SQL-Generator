**Branch:** `feat/sprint-30.8-authn-api` (from `main` `b3f520c`)

## 1. Purpose & motivation

Phase 11 roadmap's last sprint: **Authentication (AuthN)**. The system today authenticates every `/api/*` request against a **single static API key** (`configs.api_key`, plaintext, compared in `app/auth.py::verify_api_key`). 30.8 introduces **managed, hashed, multiple API keys** as a `/api/v1/api-keys` resource on the 30.0 contract.

**User-approved scope & posture:**
1. **Scope = API-key management only** — no user/password model, no login/session, no SSO. Multiple named API keys with create/list/get/revoke.
2. **Posture = inert / additive** — the new resource is a **registry + a verification contract**; the existing `verify_api_key` and every existing `/api/v1` route are **unchanged**. The registry can hash and verify a key, but it does **not** yet govern live authentication (wiring `verify_api_key` to consult the table is a deferred, breaking, user-gated step — §34).

## 2. Security design (load-bearing)

- **Store only the hash + a prefix, never the raw key or plaintext.** `key_hash = sha256(raw)`, `key_prefix = raw[:8]` (for identification in listings).
- **sha256 (stdlib `hashlib`), no salt / slow-hash.** Appropriate because API keys are **high-entropy random tokens** (`secrets.token_urlsafe(32)`), not user-chosen passwords — the industry-standard treatment (unlike passwords, which would require argon2/bcrypt). No new dependency.
- **The raw key is returned EXACTLY once** — in the `POST` create response. `GET` list/detail and every other response expose only `{id, name, key_prefix, created_at, revoked_at, active}` — never the raw key or the hash.
- **Revocation is soft** (`revoked_at` timestamp); `verify_key` only matches active (non-revoked) keys.
- The endpoints themselves are protected by the **existing** `verify_api_key` (the single config key) — managing keys still requires the current key; this does not create a bootstrapping hole (inert posture).

## 3. Existing landscape

- `app/auth.py::verify_api_key` — single-key check against `configs.api_key`. **Untouched** (inert).
- 30.0 contract + 30.1–30.7 patterns (repository idiom, guard `EXPECTED_V1_ROUTES`, snapshot regen, `rowid` ordering, `verify_api_key`, `409`/`400`/`404` usage).

## 4. Architecture

### 4.1 Persistence — `api_keys` table + repository

**Table** (`database.py::init_db`, additive):
```
api_keys(
  id          TEXT PRIMARY KEY,   -- uuid4 hex
  name        TEXT NOT NULL,
  key_prefix  TEXT NOT NULL,      -- first 8 chars of the raw key (identification only)
  key_hash    TEXT NOT NULL UNIQUE, -- sha256(raw) hex; NEVER the raw key
  created_at  TEXT NOT NULL,
  revoked_at  TEXT                -- nullable; set on revoke
)
```

**Repository** — `backend/app/api_key_repository.py`:
- `generate_and_create(name) -> tuple[str, dict]` — `raw = secrets.token_urlsafe(32)`; `key_hash = hashlib.sha256(raw.encode()).hexdigest()`; `key_prefix = raw[:8]`; insert; return `(raw, row)`. The raw is returned to the caller **once** and never stored.
- `get_api_key(id) -> dict | None`, `list_api_keys(limit, offset) -> list[dict]` (ORDER BY `rowid` DESC).
- `revoke_api_key(id) -> dict | None` — sets `revoked_at` if currently active (idempotent: returns the row either way; `None` only if the id does not exist).
- `verify_key(raw) -> dict | None` — `sha256(raw)` lookup where `revoked_at IS NULL`; returns the active row or `None`. **The inert verification contract** (not wired into `verify_api_key`).
- `row_to_response_dict(row) -> dict` — `{id, name, key_prefix, created_at, revoked_at, active}` where `active = revoked_at is None`. **Never** includes `key_hash`.

### 4.2 API — `/api/v1/api-keys` router

`backend/app/api/api_keys.py`, `verify_api_key`-protected.

**Models:**
- `ApiKeyCreate{ name: str = Field(min_length=1, max_length=200) }`.
- `ApiKeyResponse{ id, name, key_prefix, created_at, revoked_at: Optional[str], active: bool }`.
- `ApiKeyCreated(ApiKeyResponse)` + `api_key: str` — the raw key, **present only in the create response**.

**Endpoints** (canonical `ApiResponse`):
- `POST /api/v1/api-keys` → 201 `ApiResponse[ApiKeyCreated]` — the only response carrying the raw `api_key`.
- `GET /api/v1/api-keys` → 200 `ApiResponse[list[ApiKeyResponse]]` + `PageMeta` (no raw, no hash).
- `GET /api/v1/api-keys/{key_id}` → 200 `ApiResponse[ApiKeyResponse]` (missing → 404).
- `POST /api/v1/api-keys/{key_id}/revoke` → 200 `ApiResponse[ApiKeyResponse]` (idempotent; missing → 404).

(No PATCH; no hard DELETE — keys are audit records, revoked not deleted.)

### 4.3 Conformance + snapshots

Guard `EXPECTED_V1_ROUTES` gains the four api-key routes; snapshots regenerated additively (verified vs main). Protected → no security-allowlist change. No new error code.

### 4.4 What does NOT change

`app/auth.py::verify_api_key`, `configs.api_key`, and every existing route are untouched. Only additive: new table, repository, router (+1 include line), regenerated snapshots, §34. The new keys do not yet authenticate anything (inert).

## 5. Data flow

```
POST /api/v1/api-keys {name}
  → verify_api_key (existing single key)
  → generate_and_create: raw=token_urlsafe(32); store sha256(raw)+prefix (NEVER raw)
  → 201 ApiResponse[ApiKeyCreated]  (raw api_key returned ONCE)

GET /api/v1/api-keys  → list metadata only (id/name/prefix/created_at/revoked_at/active)
POST /api/v1/api-keys/{id}/revoke → set revoked_at (idempotent)
verify_key(raw) → active row | None   (inert contract; NOT wired to verify_api_key)
```

## 6. Testing strategy

- **Repository unit tests**: create returns a raw key + stores only its hash (raw not in the row; hash == sha256(raw)); `verify_key(raw)` matches an active key and returns None after revoke / for a wrong key; list/get metadata; revoke idempotent + sets revoked_at; row_to_response_dict never contains key_hash; two creates get distinct keys/hashes.
- **Endpoint tests**: POST returns the raw `api_key` once + 201 envelope; GET list/detail never contain `api_key`/`key_hash`; revoke flips `active` to False; 404 on missing; `X-Request-ID`; 403 without the (existing) API key.
- **Conformance**: guard covers the four api-key routes.
- `fastapi` pinned `0.115.12`.

## 7. Deliberately out of scope (→ TECH-DEBT §34)

- **Live enforcement** — wiring `verify_api_key` (or a new dependency) to authenticate requests against the `api_keys` table instead of / in addition to the single config key. This is a **breaking**, user-gated migration (existing clients use the single key); deferred.
- **User accounts / passwords / login / sessions / JWT / SSO** (not this scope).
- **Per-key scopes / permissions / expiry / rotation reminders / rate limits.**
- **Key-usage audit trail, last-used timestamp.**
- **Admin-role gating** (managing keys uses the same `verify_api_key` as everything else; RBAC awaits a real role model).
- **Retiring the plaintext `configs.api_key`.**
