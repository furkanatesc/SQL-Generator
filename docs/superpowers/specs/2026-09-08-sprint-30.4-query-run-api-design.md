# Sprint 30.4 — Query Run API (Design Spec)

**Date:** 2026-09-08
**Phase:** 11 (API / Backend Productization) — fifth sprint
**Branch:** `feat/sprint-30.4-query-run-api` (from `main` `d84a370`)
**Predecessor:** 30.3 Schema Sync API (PR #172). 30.4 adds the fourth `/api/v1` resource, linking to a **connection**.

---

## 1. Purpose & motivation

Phase 11 roadmap: … Connection Registry → Schema Sync → **Query Run** → Query History → … A query-run records the execution of a SQL query against a registered connection.

**Scope choice (user-approved): inert / record-only.** Consistent with 30.0–30.3, which never open a live DB connection, 30.4 does **not** execute anything and does **not** resolve a connection's `secret_ref`. A query-run **records** a run against a connection — the SQL and, optionally, a **provided outcome** (result rows or an execution error — the payload a future live executor / 29.x adapter would produce). Live execution (resolving the secret, opening a read-only connection, running the SELECT) is deferred to a later sprint and is a user-gated, security-sensitive step (TECH-DEBT §26/§28/§30).

This mirrors 30.3's "schema provided in the request" pattern: 30.3 stores a provided schema; 30.4 stores a provided result.

## 2. Scope decisions (user-approved / author-decided; documented for veto)

1. **Inert / record-only** — 30.4 executes nothing and resolves no secret. *(User-approved.)*
2. **A run may carry a provided outcome** — optional `result` (columns/rows/truncated/duration_ms) or an `execution_error`; status is derived (`recorded` / `succeeded` / `failed`). Absent a result, status is `recorded` (awaiting execution).
3. **Per-connection**, `connection_id` validated to exist → 400. Append-only history, no PATCH; DELETE allowed.
4. **Result shape aligned with 29.x** `SQLDatabaseExecutionResult` (rows/row_count/truncated/execution_error/duration_ms) for forward-compatibility, but stored as a simple JSON payload (not the full frozen dataclass).

## 3. Existing landscape

- 30.2 `connection_repository.get_connection` (existence check).
- 29.x `SQLDatabaseExecutionResult` (`multi_database_execution.py`) — the canonical execution-result shape 30.4 aligns to (not imported/constructed; used only as the field template).
- 30.0 contract + 30.1–30.3 patterns (repository idiom, guard `EXPECTED_V1_ROUTES`, snapshot regen, `400` on unknown reference, DELETE bool-gate, `rowid` ordering, `verify_api_key`).

## 4. Architecture

### 4.1 Persistence — `query_runs` table + repository

**Table** (`database.py::init_db`, additive; + `connection_id` index):
```
query_runs(
  id              TEXT PRIMARY KEY,      -- uuid4 hex
  connection_id   TEXT NOT NULL,         -- references connections(id)
  sql             TEXT NOT NULL,
  status          TEXT NOT NULL,         -- "recorded" | "succeeded" | "failed"
  row_count       INTEGER,               -- nullable (null when recorded)
  columns_json    TEXT,                  -- JSON list[str], nullable
  rows_json       TEXT,                  -- JSON list[list], nullable
  truncated       INTEGER,               -- 0/1, nullable
  execution_error TEXT,                  -- nullable
  duration_ms     REAL,                  -- nullable
  created_at      TEXT NOT NULL
)
```

**Repository** — `backend/app/query_run_repository.py`:
- `create_query_run(connection_id, sql, result=None) -> dict` — `result` is `None` (→ status `recorded`) or a dict `{columns?, rows?, truncated?, execution_error?, duration_ms?}`. Status derivation: `execution_error` present → `failed`; else rows/columns present → `succeeded` (`row_count = len(rows)`); else (`result` given but empty) → `succeeded` with row_count 0. Store JSON fields.
- `get_query_run(id)`, `list_query_runs(limit, offset, connection_id=None, status=None)` (ORDER BY `rowid` DESC), `delete_query_run(id) -> bool`, `row_to_response_dict(row)` (parse JSON; nest `result` = `{columns, rows, truncated, duration_ms}` or `None` when recorded; `execution_error` top-level).

### 4.2 API — `/api/v1/query-runs` router

`backend/app/api/query_runs.py`, `verify_api_key`-protected.

**Models:**
- `QueryRunResult{ columns: list[str] = [], rows: list[list] = [], truncated: bool = False, duration_ms: Optional[float] = None }`.
- `QueryRunCreate{ connection_id: str, sql: str(min_length=1), result: Optional[QueryRunResult] = None, execution_error: Optional[str] = None }`.
- `QueryRunResponse{ id, connection_id, sql, status, row_count: Optional[int], result: Optional[QueryRunResult], execution_error: Optional[str], created_at }`.

**Endpoints** (canonical `ApiResponse`):
- `POST /api/v1/query-runs` → 201; unknown `connection_id` → 400. (`execution_error` set → failed; `result` set → succeeded; neither → recorded.)
- `GET /api/v1/query-runs` → 200 list + `PageMeta`; optional `?connection_id=` and `?status=` filters.
- `GET /api/v1/query-runs/{run_id}` → 200 (missing → 404).
- `DELETE /api/v1/query-runs/{run_id}` → 200 (bool-gated; missing → 404).

(No PATCH — runs are immutable history.)

### 4.3 Conformance + snapshots

Guard `EXPECTED_V1_ROUTES` gains the four query-run routes; snapshots regenerated additively (verified vs main). Protected → no security-allowlist change.

### 4.4 What does NOT change

No existing table/endpoint/handler behavior changes; the 29.x execution contract is used only as a field template (not imported/constructed). Only additive: new table(+index), repository, router (+1 include line), regenerated snapshots, §30. No new error code (400/404/422 exist).

## 5. Data flow

```
POST /api/v1/query-runs {connection_id, sql, result?|execution_error?}
  → verify_api_key
  → connection_repository.get_connection(connection_id) is None -> 400
  → derive status (recorded / succeeded / failed); store append-only row
  → 201 ApiResponse[QueryRunResponse]   (NO live execution, NO secret resolution)
```

## 6. Testing strategy

- **Repository unit tests**: recorded (no result); succeeded (result rows → row_count); failed (execution_error → status failed); list + connection/status filters + paginate; get/delete; JSON round-trip.
- **Endpoint tests**: CRUD-ish; canonical envelope + `X-Request-ID`; 201 for each status; 400 unknown connection; 404; `?connection_id`/`?status` filters + `PageMeta`; 403 without key.
- **Conformance**: guard covers the query-run routes.
- `fastapi` pinned `0.115.12`.

## 7. Deliberately out of scope (→ TECH-DEBT §30)

- **Live execution** — resolving `secret_ref`, opening a read-only connection, running the SELECT (29.x adapters). This is the security-sensitive, user-gated step deferred to a later sprint.
- **NL→SQL generation** (the pipeline / `jobs` flow) — 30.4 records a SQL run, it does not generate SQL from natural language.
- **Result pagination/streaming, large-result storage limits, run cancellation, retries.**
- **Workspace-scoping, connection-delete cascade** (dangling `connection_id` possible; consistent with 30.2/30.3 deferral).
- **Cursor pagination / cross-page `total`; run mutation (PATCH).**
