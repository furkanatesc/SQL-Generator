# Sprint 26.4 — Sensitive Table / Column Policy · Design

**Phase 7 (Security & Governance) · Contract-first, no execution · 2026-06-20**

## 1. Purpose

Define a deterministic, static (no-execution) backend contract that decides
whether a query touches **declared-sensitive** tables/columns and, if so, what to
do about it. Where 26.0 answers "may this action run?", 26.1 "right tenant?", 26.2
"is it read-only?", and 26.3 "how risky/expensive?", 26.4 answers:

* Does this query reference any table/column that the operator has **declared
  sensitive**, and is touching it allowed, denied, or does it require approval?

It is a **policy gate that also emits a signal**: it returns a decision
(`ALLOW`/`DENY`/`REQUIRES_APPROVAL`) plus, for audit, which sensitive resources
matched and the maximum sensitivity level. The signal part does not compete with
the decision — it explains it (consumed by 26.6 audit, 26.7 approval).

This is a **declaration-based** gate: it enforces only what the policy author
declared sensitive. Heuristic content detection (PII/PHI by value/name patterns)
is 26.5, deliberately out of scope here.

## 2. Scope

**In scope:** the contract — enums, immutable policy rule, immutable
request/result, a stateless evaluator, JSON-safe secret-free `to_dict()`,
best-effort SQL reference extraction as a fallback, and exhaustive unit tests.

**Out of scope (later sprints / deliberate):** PII/PHI content detection (26.5),
audit persistence (26.6), approval workflow orchestration (26.7), real SQL parser,
alias/schema resolution, catalog metadata, any I/O, DB driver, adapter execution,
API/UI, tenant/RBAC/AuthN.

## 3. Module layout

- `backend/app/security/sql_sensitive_data_policy.py`
- `backend/app/tests/security/test_sql_sensitive_data_policy.py`
- Exported from `backend/app/security/__init__.py` (mirrors 26.0–26.3).
- Contract version: `sql_sensitive_data_policy_contract_v1`.
- Reuses the shared `app.security._sql_text` sanitizer (`to_executable_core`,
  `leading_keyword`) so keywords/identifiers inside string literals or comments are
  never matched. Performs no I/O.

## 4. Enums

```python
class SQLSensitivityLevel(str, Enum):       # ordered low -> high
    PUBLIC = "public"
    INTERNAL = "internal"
    CONFIDENTIAL = "confidential"
    RESTRICTED = "restricted"

class SQLSensitiveDataDecision(str, Enum):  # own enum (independent of 26.0)
    ALLOW = "allow"
    DENY = "deny"
    REQUIRES_APPROVAL = "requires_approval"

class SQLSensitiveResourceType(str, Enum):
    TABLE = "table"
    COLUMN = "column"

class SQLSensitiveDataReasonCode(str, Enum):
    NO_SENSITIVE_MATCH = "no_sensitive_match"
    SENSITIVE_MATCH_ALLOW = "sensitive_match_allow"
    SENSITIVE_MATCH_REQUIRES_APPROVAL = "sensitive_match_requires_approval"
    SENSITIVE_MATCH_DENY = "sensitive_match_deny"
    UNUSABLE_INPUT = "unusable_input"

class SQLSensitiveDataEvaluatedVia(str, Enum):
    EXPLICIT_REFERENCES = "explicit_references"   # sound
    SQL_EXTRACTION = "sql_extraction"             # best-effort
    NONE = "none"                                 # no usable input
```

Severity ordering (`_LEVEL_ORDER`) and decision restrictiveness ordering
(`DENY > REQUIRES_APPROVAL > ALLOW`) are module-level maps, deterministic.

## 5. Policy rule (trusted config)

```python
@dataclass(frozen=True)
class SQLSensitiveDataRule:
    resource_type: SQLSensitiveResourceType   # MUST be a real enum (trusted config)
    resource_id: str                          # normalized lowercase: "users" or "users.ssn"
    sensitivity_level: SQLSensitivityLevel
    action: SQLSensitiveDataDecision          # independent of level
    policy_id: Optional[str] = None           # domain tag, e.g. "pci", "hr-only"
```

- Validated in `__post_init__`: enum members required, `resource_id` non-empty
  string; COLUMN ids should contain a `.` (table-qualified) — normalized to
  lowercase. Rules are config, not untrusted input (same trust stance as 26.0).
- `sensitivity_level` and `action` are **independent**: a rule may be
  `CONFIDENTIAL + DENY` or `RESTRICTED + REQUIRES_APPROVAL`. The level is the
  signal; the action is the gate.

## 6. Request (hybrid reference source)

```python
@dataclass(frozen=True)
class SQLSensitiveDataPolicyRequest:
    version: str
    sql: Optional[str] = None
    referenced_tables: Optional[Sequence[str]] = None
    referenced_columns: Optional[Sequence[str]] = None
    dialect: str = "generic"
```

- `version` mismatch → raises `SQLSensitiveDataPolicyContractError` (contract
  violation). All other malformed input yields a fail-closed **result**, never a
  raise (mirrors 26.3's "bad SQL → CRITICAL result, not exception").
- **Reference resolution (hybrid):**
  1. If `referenced_tables`/`referenced_columns` are provided → use them verbatim
     (normalized lowercase). This is the **sound** path → `evaluated_via =
     EXPLICIT_REFERENCES`.
  2. Else if `sql` is a non-empty string → best-effort regex extraction over
     `to_executable_core(sql)` → `evaluated_via = SQL_EXTRACTION`.
  3. Else (neither, or `sql` non-string/empty) → no usable input.

## 7. Evaluation flow

1. Validate request type & version (version mismatch raises).
2. Resolve references (§6). If no usable input → `DENY / UNUSABLE_INPUT`,
   `sensitivity_level = PUBLIC`, `evaluated_via = NONE` (fail-closed: cannot
   confirm absence of sensitive access).
3. **Fail-closed extraction rule:** on the `SQL_EXTRACTION` path, if `SELECT *` or
   `<alias>.*` is present, treat **every COLUMN rule whose table is among the
   referenced tables** as matched (we cannot see which columns `*` expands to, so
   assume all sensitive ones are touched).
4. Match policy rules:
   - TABLE rule matches if its `resource_id` is among referenced tables.
   - COLUMN rule matches if its `resource_id` is among referenced columns
     (normalized dotted name) **or** via the `SELECT *` fail-closed rule (§3).
5. Aggregate:
   - `decision` = most restrictive matched action (`DENY > REQUIRES_APPROVAL >
     ALLOW`); no match → `ALLOW`.
   - `sensitivity_level` = max level among matched rules; no match → `PUBLIC`.
   - `reason_code` derived from (match? + decision).
6. Build result; `matched` de-duplicated and deterministically ordered (by
   level desc, then resource_type, then resource_id).

## 8. Result (immutable, audit-grade, secret-free)

```python
@dataclass(frozen=True)
class SQLSensitiveDataPolicyResult:
    version: str
    decision: SQLSensitiveDataDecision
    sensitivity_level: SQLSensitivityLevel
    matched: Tuple[SQLSensitiveDataMatch, ...]   # (resource_type, resource_id, level, action, policy_id)
    reason_code: SQLSensitiveDataReasonCode
    reason: str
    sql_sha256: Optional[str]
    evaluated_via: SQLSensitiveDataEvaluatedVia
    dialect: str
    def to_dict(self) -> Dict[str, Any]: ...     # JSON-safe; enum .value's; no raw SQL
```

- Carries **no raw SQL** — only `sql_sha256` (when sql was given) plus
  policy-declared resource names (schema metadata declared by the operator, not
  secrets).
- `matched` entries are a small frozen `SQLSensitiveDataMatch` dataclass for a
  stable, typed audit shape.

## 9. Best-effort SQL extraction (fallback only)

Regex over the sanitized executable core:

- **Tables:** identifiers following `FROM` / `JOIN` (optional `schema.` prefix,
  optional alias) up to the next top-level clause boundary; comma-joins split at
  paren-depth 0 (reuse the depth scanner style from 26.3).
- **Columns:** qualified `table.column` / `alias.column` tokens in the statement,
  plus the `SELECT *` fail-closed expansion.

This path is explicitly **best-effort and under-detection-biased** and is flagged
via `evaluated_via = SQL_EXTRACTION` so a strict caller can require explicit
references instead.

## 10. Documented limitations (26.3-style honesty)

- `SQL_EXTRACTION` is alias-blind, nesting-blind, and schema-qualification-blind:
  it can miss columns referenced through aliases (`u.ssn` is not auto-resolved to
  `users.ssn`), inside subqueries/CTEs, or via `*` on tables without a column
  rule. **Sound usage = explicit references.** A real parser or catalog metadata
  is the sound fix (later sprint).
- Matching is on normalized dotted names; alias/schema resolution is out of scope.
- A table not present in the policy is never treated as sensitive — this is a
  **declaration-based** gate. Content/name heuristics are 26.5.
- The `SELECT *` fail-closed rule can over-match (flag a sensitive column that a
  later real projection would have excluded) — intentional bias to higher
  protection on the lossy path.

## 11. Test matrix

- Empty policy → every query `NO_SENSITIVE_MATCH / ALLOW`.
- Explicit-reference happy paths: table match, column match, no match.
- Extraction happy paths: `FROM`/`JOIN` table extraction, `table.column`
  extraction.
- `SELECT *` fail-closed column expansion (matches column rules of referenced
  tables).
- Every `SQLSensitivityLevel` x every `SQLSensitiveDataDecision` rule.
- Most-restrictive decision aggregation (DENY beats APPROVAL beats ALLOW).
- Max-level aggregation across multiple matches.
- Unusable input (no refs, no sql, non-string sql, empty sql) → `DENY /
  UNUSABLE_INPUT`, `evaluated_via = NONE`.
- Version mismatch (request & result) → raises.
- Rule validation: bad enum, empty resource_id → raises at construction.
- Immutability (`FrozenInstanceError`), `matched` de-dup & deterministic order.
- `to_dict()` JSON-serializable, secret-free (no raw SQL), round-trips enum values.
- Normalization: case-insensitive table/column matching.

- New module + tests; all tests green; no regression in existing security tests.
