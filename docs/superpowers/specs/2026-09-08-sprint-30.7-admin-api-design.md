# Sprint 30.7 — Admin API (Design Spec)

**Date:** 2026-09-08
**Phase:** 11 (API / Backend Productization) — eighth sprint
**Branch:** `feat/sprint-30.7-admin-api` (from `main` `9853af5`)
**Predecessor:** 30.6 Feedback API (PR #175).

---

## 1. Purpose & motivation

Phase 11 roadmap: … Feedback → **Admin** → AuthN. 30.7 adds an operator-facing admin surface under `/api/v1/admin`, on the 30.0 contract — a read-only snapshot of the runtime configuration and the Phase 11 resource population.

Runtime diagnostics already exist (`app/health.py::build_health_response().config` → `RuntimeConfigDiagnostics`: environment, debug flag, CORS count, upload/API-key configured, startup warning counts). 30.7 **reuses** that and adds simple resource counts over the Phase 11 tables.

**Scope decision (user-approved: continue inert resources; author-decided shape):** a **read-only** admin composite — no dangerous admin operations (no writes, no cache-clear, no user management). It reuses existing services (health diagnostics) + `COUNT(*)` over the 30.x tables. No new table.

## 2. Scope decisions

1. **Read-only** — two `GET` endpoints; no writes / destructive ops.
2. **Reuse** `build_health_response().config` for the config diagnostics; **no** duplication of the heavier 27.7 dashboard/trace surface (`/api/dashboard` stays as-is).
3. **No new table** — `admin_repository` computes `COUNT(*)` over `workspaces`/`connections`/`schema_syncs`/`query_runs`/`query_run_feedback`.
4. **Protected** (`verify_api_key`).

## 3. Existing landscape (reused)

- `app/health.py::build_health_response()` → `HealthResponse.config` (`RuntimeConfigDiagnostics`, in `app/api/schemas.py`).
- `app/settings.py::get_settings()` (environment, debug flag).
- Phase 11 tables (30.1–30.6): `workspaces`, `connections`, `schema_syncs`, `query_runs`, `query_run_feedback`.
- 30.0 contract + 30.1–30.6 patterns (guard `EXPECTED_V1_ROUTES`, snapshot regen, `verify_api_key`).
- 27.7 `app/api/dashboard_api.py` / `dashboard_service.py` — the heavier observability surface, left as-is (not wrapped).

## 4. Architecture

### 4.1 Repository — `admin_repository.py` (read-only counts)

New `backend/app/admin_repository.py`:
- `resource_counts() -> dict[str, int]` — one query per Phase 11 table: `SELECT COUNT(*) FROM <t>` for `workspaces`, `connections`, `schema_syncs`, `query_runs`, `query_run_feedback`; returns `{"workspaces": n, "connections": n, "schema_syncs": n, "query_runs": n, "query_run_feedback": n}`. Table names are a fixed internal tuple (no user input); read-only.

### 4.2 API — `/api/v1/admin` router

New `backend/app/api/admin.py`, `verify_api_key`-protected.

**Models:**
- `ResourceCounts{ workspaces: int, connections: int, schema_syncs: int, query_runs: int, query_run_feedback: int }`.
- `AdminOverview{ environment: str, debug_endpoints_enabled: bool, app_version: str, resources: ResourceCounts }`.
- Config diagnostics reuse `app.api.schemas.RuntimeConfigDiagnostics`.

**Endpoints** (canonical `ApiResponse`):
- `GET /api/v1/admin/overview` → `ApiResponse[AdminOverview]` — `environment`/`debug_endpoints_enabled`/`app_version` from `get_settings()`, `resources` from `admin_repository.resource_counts()`.
- `GET /api/v1/admin/config` → `ApiResponse[RuntimeConfigDiagnostics]` — from `build_health_response().config`.

No path-param routes → no ordering collision.

### 4.3 Conformance + snapshots

Guard `EXPECTED_V1_ROUTES` gains the two admin routes; snapshots regenerated additively (verified vs main). Protected → no security-allowlist change.

### 4.4 What does NOT change

`health.py`, `settings.py`, the 27.7 dashboard, and all Phase 11 tables are read, not modified. Only additive: new repository, router (+1 include line), regenerated snapshots, §33. No new table, no error code.

## 5. Data flow

```
GET /api/v1/admin/overview
  → verify_api_key
  → get_settings() (environment, debug, version) + admin_repository.resource_counts()
  → ApiResponse[AdminOverview]

GET /api/v1/admin/config
  → build_health_response().config  (RuntimeConfigDiagnostics)
  → ApiResponse[RuntimeConfigDiagnostics]
```

## 6. Testing strategy

- **Repository unit tests**: `resource_counts` returns all five keys; counts reflect seeded rows per table; zero when empty.
- **Endpoint tests**: overview envelope + fields + resource counts reflecting created resources; config envelope + diagnostics shape; envelope + `X-Request-ID`; 403 without key.
- **Conformance**: guard covers the two admin routes.
- `fastapi` pinned `0.115.12`.

## 7. Deliberately out of scope (→ TECH-DEBT §33)

- **Admin operations / writes** — no cache-clear, config mutation, resource purge, user/role management (that is AuthN 30.8 + later).
- **Wrapping the 27.7 dashboard / 27.6 metrics / 27.8 LLM-usage** under `/api/v1/admin` (they remain on their legacy `/api/*` paths).
- **Per-workspace scoping of counts, time-series/trend metrics.**
- **RBAC / admin-only authz** — the endpoints use the same `verify_api_key` as the rest of `/api/v1`; a distinct admin role awaits AuthN (30.8).
