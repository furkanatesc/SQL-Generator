# Sprint 32.11 — CI/CD Release Pipeline + Staging (Design)

Phase 13 · Branch `feat/32.11-release-pipeline` · Önceki: 32.0 (yerel build'li prod compose), 32.1–32.10.

## 1. Problem & karar

İmajlar yalnız hedef host'ta `docker compose up --build` ile yerelde üretiliyor (TECH-DEBT §36.6): sürümlü, yeniden
üretilebilir, test edilmiş bir artefakt yok; `/health` her zaman `0.1.0` raporluyor; staging ortamı tanımlı değil;
sürüm çıkarma prosedürü yok.

**Karar (kapsam):**
1. **`.github/workflows/release.yml`** — yalnız `v*.*.*` tag push'u ve elle `workflow_dispatch` (sürüm girdisi) ile:
   - `verify`: backend test süiti + frontend build (release'i bozuk koddan çıkarmamak için; tam CI'ın hızlı alt kümesi).
   - `publish` (`packages: write`): backend + frontend imajlarını **GHCR**'a (`ghcr.io/<owner>/sqlgen-backend|frontend`)
     `<version>`, `<major>.<minor>` ve `sha-<short>` etiketleriyle; OCI label'ları; backend'e `APP_VERSION` build-arg.
   - `staging-smoke`: yayınlanan imajları **çeker** (build yok), prod compose + **staging overlay** ile ayağa kaldırır,
     `/ready` (hiçbir bileşen fail değil), `/health` sürümü = tag, SPA ve bir job'un worker'da yürümesini doğrular.
   - `github-release` (`contents: write`): tag için GitHub Release (otomatik notlar).
2. **Sürüm imaja gömülü**: backend Dockerfile `ARG APP_VERSION=0.1.0` → `ENV NL2SQL_APP_VERSION` (yerel build davranışı aynı);
   frontend'e OCI version label.
3. **Registry'den çalıştırma**: prod compose imaj adları `${SQLGEN_IMAGE_REGISTRY:-}sqlgen-…:${SQLGEN_IMAGE_TAG:-latest}`
   (boş önek = bugünkü yerel imajlar); operatör `docker compose pull && up -d --no-build`.
4. **`docker-compose.staging.yml` overlay**: ayrı compose proje adı (`sqlgen-staging` → ayrı volume'lar/ağ),
   `NL2SQL_ENVIRONMENT=production-staging` (production-like: tüm prod güvenlik kontrolleri aktif), aynı host'ta prod'un
   yanında farklı portlarla (`.env.staging`).
5. Runbook: sürüm çıkarma (tag), registry'den deploy, staging, geri dönüş (önceki tag + 32.8 yedek).

Seçilmeyen:
- (a) Otomatik prod deploy (CD → sunucuya SSH) — hedef sunucu/kimlik bilgisi yok, geri alınması zor dış etki; deploy
  operatör adımı (§47).
- (b) Docker Hub — ek secret; GHCR `GITHUB_TOKEN` ile çalışır.
- (c) Her `main` push'unda imaj yayını — yalnız bilinçli sürümler (tag) yayınlanır; PR CI zaten her değişikliği build eder.
- **Bu sprint tag push etmez** (dış etkili yayın kullanıcı kararıdır); workflow PR'da YAML sözleşme testleriyle ve
  `docker compose config` ile doğrulanır.

## 2. Verify
`backend/tests/test_release_pipeline_contract.py`: tetikleyiciler (yalnız tag + dispatch), job zinciri
(verify→publish→staging-smoke→github-release), en az yetki (job-level `packages`/`contents: write`), imaj adları/etiketler,
`APP_VERSION` build-arg, staging smoke'un `--no-build` ve overlay kullanması; Dockerfile ARG/ENV/label; compose
registry öneki + `.env.prod.example`; staging overlay (proje adı, production-like ortam, literal secret yok). CI
prod-compose-smoke: `docker compose -f prod -f staging config -q`. Full suite + CI 5/5.

## 3. Out of scope (TECH-DEBT §47)
- Otomatik prod/staging sunucu deploy'u (SSH/Kubernetes), onay kapıları (GitHub environments).
- İmaj imzalama (cosign), SBOM, güvenlik taraması (Trivy).
- Çok mimarili (arm64) imajlar.
- Migration'ların deploy öncesi ayrı adımda çalıştırılması.
