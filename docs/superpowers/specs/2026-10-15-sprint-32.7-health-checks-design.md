# Sprint 32.7 — Health Checks (Design)

Phase 13 · Branch `feat/32.7-health-checks` · Önceki: 32.2–32.6 (her biri yeni startup uyarıları ekledi).

## 1. Problem & karar

`/ready` yalnız dört boolean + kritik uyarı sayısı döndürüyor: 503 alındığında **hangi bileşenin neden** düştüğü
görünmüyor (operatör log'a bakmak zorunda). 32.2–32.6'nın uyarıları (secret dosyası, migration, kuyruk, ...) tek
sayıya eziliyor. Disk doluluğu (SQLite yazamaz) hiç kontrol edilmiyor; LLM key'i yoksa job'lar sessizce başarısız
oluyor. Worker healthcheck'i yalnız liveness dosyasına bakıyor, DB'ye erişip erişemediğini bilmiyor.

**Karar (kapsam):** `/ready`'ye **bileşen-bazlı `checks`** (additive) + **disk alanı** kontrolü + **LLM key** durumu +
**worker healthcheck'ine DB erişimi**. `/health` (liveness) sözleşmesi değişmez.

- Her bileşen: `{"status": "ok" | "degraded" | "fail", "reason": <kısa kod> | null}`. Yalnız sabit isimler ve
  kodlar — yol, değer, secret yok (`/ready` kimlik doğrulamasız).
- Readiness kuralı aynı kalır (DB erişilebilir + API key + upload yazılabilir + kritik uyarı yok) **ve** disk
  `fail` değil. `degraded` hiçbir zaman 503 yapmaz.

Seçilmeyen:
- (a) `/health`'i hafifletmek (her probe'da tam doğrulama çalışıyor) — `HealthResponse.config` sözleşmesi
  doğrulama sayılarını içeriyor; değiştirmek breaking. Maliyet küçük (birkaç SQLite sorgusu); TECH-DEBT §43.
- (b) Ayrı kimlik doğrulamalı `/api/v1/admin/health` — aynı bilgi `/ready`'de güvenli kodlarla verilebiliyor;
  ikinci yüzey drift riski.
- (c) LLM sağlayıcısına canlı ping — maliyet + rate limit + dış bağımlılık probe'u kırar; yalnız yapılandırma.

## 2. Design

### 2.1 Bileşenler (`app/health.py::build_component_checks`)
| Bileşen | fail | degraded |
|---|---|---|
| `database` | `SELECT 1` başarısız (`unreachable`) | — |
| `migrations` | `DB_MIGRATIONS_PENDING` / `DB_SCHEMA_AHEAD` | — |
| `api_key` | `API_KEY_NOT_CONFIGURED` / `API_KEY_INSECURE_DEFAULT` | `API_KEY_ENV_SHADOWED` |
| `secrets` | `SECRET_FILE_UNREADABLE` | `SECRET_SOURCE_CONFLICT` |
| `upload_dir` | `UPLOAD_DIR_NOT_WRITABLE` / `UPLOAD_DIR_NOT_FOUND` | — |
| `job_queue` | — | `JOB_QUEUE_STALLED` |
| `disk` | boş alan < `NL2SQL_HEALTH_MIN_FREE_DISK_MB` (`low_disk_space`) | < 2× eşik (`disk_space_low_soon`) |
| `llm` | — | LLM key yok (`llm_key_not_configured`; job'lar başarısız olur) |
| `config` | diğer kritik uyarılar (ör. CORS wildcard, debug endpoint'leri) | diğer uyarılar (ör. `UNKNOWN_CONFIG_ENV_VAR`) |

`reason` = ilgili uyarı kodunun küçük harfi ya da yukarıdaki sabit kod; birden çok neden varsa en ağırı.
Disk ölçümü app DB'sinin dizini (`shutil.disk_usage`); ayar `0` ise kontrol kapalı (`ok`, reason `disabled`).

### 2.2 Sözleşme
`ComponentCheck` modeli; `ReadinessResponse.checks: Dict[str, ComponentCheck]` (varsayılan boş — additive);
snapshot regenerate. Bilgi `validate_runtime_config()` tek çağrısından türetilir (mevcut testlerin mock deseni
korunur).

### 2.3 Worker healthcheck
`python -m app.jobs.worker healthcheck` = liveness dosyası taze **ve** app DB'de `SELECT 1` başarılı.

### 2.4 Ayar
`NL2SQL_HEALTH_MIN_FREE_DISK_MB` (100, ≥0; 0 = kapalı).

## 3. Verify
`backend/tests/test_health_checks.py`: her bileşenin fail/degraded eşlemesi, disk eşikleri (mock), LLM key,
degraded 200 / fail 503, eski boolean alanlar aynı, `/ready` gövdesinde yol/secret yok, worker healthcheck DB
koşulu. Mevcut `test_readiness_diagnostics.py` değişmeden geçer. Snapshot additive. Full suite + CI 5/5 (smoke
`/ready` `checks.database.status == ok`).

## 4. Out of scope (TECH-DEBT §43)
- `/health` liveness'ın her probe'da tam doğrulama çalıştırması (hafif `/livez` ayrımı).
- LLM sağlayıcısı / Qdrant canlı erişilebilirlik kontrolü.
- Bileşen bazlı Prometheus metrikleri (→ 32.9 Logging/observability ile değerlendirilecek).
- Frontend'de sağlık paneli.
