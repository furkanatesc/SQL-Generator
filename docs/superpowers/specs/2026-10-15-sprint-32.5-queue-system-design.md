# Sprint 32.5 — Queue System (Design)

Phase 13 · Branch `feat/32.5-queue-system` · Önceki: 32.4 (worker process, `jobs` claim modeli).

## 1. Problem & karar

32.4 job'ları ayrı worker'a taşıdı ama kuyruk "ilk gelen, bir kez" semantiğinde: geçici bir LLM kesintisi ya da
ölen worker job'u kalıcı `failed` yapar; acil iş öne alınamaz; çok worker LLM sağlayıcısını aynı anda
boğabilir; tükenmiş job'ları görmenin/yeniden kuyruğa almanın operatör yolu yok (TECH-DEBT §40.1).

**Karar (kapsam):** 32.5 = 32.4'ün **`jobs` tablosu kuyruğunun üstüne** kuyruk semantiği:
1. **Retry + üstel backoff** (yalnız worker modunda): geçici başarısızlık (tüm pipeline denemeleri `llm_api_error`)
   ve heartbeat'i kaybolmuş job → `attempts < max_attempts` ise `pending` + `next_attempt_at`; değilse
   `failed` + **dead-letter** (`dead_lettered_at`).
2. **Öncelik**: `priority` (-10..10, varsayılan 0); claim `priority DESC, created_at`.
3. **Global eşzamanlılık limiti**: `NL2SQL_JOB_MAX_CONCURRENT` (0 = sınırsız) — tüm worker'lar toplamında
   aynı anda `processing` job sayısı (LLM rate koruması).
4. **Operatör yüzeyi**: `GET /api/v1/admin/queue` (durum sayıları, retry bekleyen, dead-letter, en eski bekleyen
   yaşı, ayarlar) ve `POST /api/v1/admin/jobs/{job_id}/requeue` (yalnız `failed` → `pending`, sayaçlar sıfır).

Seçilmeyen:
- (a) Redis/RabbitMQ/Celery broker — yeni stateful servis + bağımlılık; mevcut ölçek (tek host, SQLite, tek-hane
  worker sayısı) için `jobs` tablosu yeterli ve job durumu zaten orada. Kuyruk mantığı `app/jobs/queue_policy.py`
  + repository'de toplandığı için ileride broker'a geçiş sınırı net.
- (b) Deterministik başarısızlıkları (validation, şema, eksik LLM key) yeniden denemek — aynı sonucu üretir,
  LLM maliyeti; yalnız geçici sınıflar retry edilir.
- (c) Yeni `dead` job durumu — `JobStatus` enum'u, API sözleşmesi ve frontend aynasını değiştirir; dead-letter
  `failed` + `dead_lettered_at` ile ifade edilir (API durumu değişmez).
- (d) Inline modda retry — `BackgroundTasks`'ın kuyruğu yok; inline dev/test modudur.

## 2. Design

### 2.1 Şema — APP_MIGRATIONS v3 `queue`
`jobs`: `priority INTEGER NOT NULL DEFAULT 0`, `attempts INTEGER NOT NULL DEFAULT 0`,
`next_attempt_at TEXT`, `dead_lettered_at TEXT`; index `idx_jobs_queue (status, priority, created_at)`.

### 2.2 `app/jobs/queue_policy.py` (saf)
- `is_transient_failure(result) -> bool`: başarısız ve ≥1 deneme ve **tüm** denemelerin validation hataları
  yalnız `llm_api_error`.
- `backoff_seconds(attempt, base, cap=900) = min(cap, base * 2**(attempt-1))`.
- `decide_failure(attempts, max_attempts, transient) -> "retry" | "dead_letter" | "fail"`:
  geçici & attempts < max → retry; geçici & tükendi → dead_letter; geçici değil → fail.

### 2.3 Repository
- `claim_next_job(worker_id, max_concurrent=0)`: `pending` ve (`next_attempt_at` NULL ya da ≤ şimdi) ve
  (limit 0 ya da `processing` sayısı < limit); `priority DESC, created_at, rowid`; `attempts += 1`.
- `schedule_retry(job_id, delay, error_message, error_code)` → `pending`, `next_attempt_at`, hata alanları son
  hatayla (izlenebilirlik), `worker_id`/`claimed_at`/`heartbeat_at` temizlenir.
- `dead_letter(job_id, error_message, error_code)` → `failed` + `dead_lettered_at`.
- `recover_stale_jobs(stale_seconds, max_attempts, base_backoff)` → heartbeat'i kaybolan `processing` job'ları
  retry ya da dead-letter (ölen worker = geçici); `(requeued, dead_lettered)` döner.
- `requeue_job(job_id)` → yalnız `failed`: `pending`, attempts=0, `next_attempt_at`/`dead_lettered_at`/hata/sonuç
  temizlenir; değilse `None`/`False` (API 404/409).
- `queue_stats()` → admin metrikleri.
- `count_stalled_pending` artık `COALESCE(next_attempt_at, created_at)` kullanır (backoff bekleyen job stalled sayılmaz).

### 2.4 Executor / worker
`execute_job(..., on_failure=None)`: başarısızlıkta `on_failure(message, error_code, transient)` True dönerse
executor `failed` yazmaz. Pipeline sonucu için `transient = is_transient_failure(res)`; beklenmeyen exception'lar
geçici sayılmaz (ör. eksik key). Worker `on_failure`'ı `decide_failure`'a bağlar (retry → `schedule_retry`,
dead_letter → `dead_letter`, fail → False = executor'ün normal yolu). Inline: `on_failure` yok (bugünkü davranış).
Worker: stale kurtarma `recover_stale_jobs`'a geçer.

### 2.5 API
- `JobCreateRequest.priority: int = 0` (`ge=-10, le=10`) — `POST /api/jobs/without-file`; upload Form'u değişmez.
- Admin router'a 2 route (30.0 kanonik `ApiResponse`; conformance allowlist + snapshot regenerate, additive).
  Requeue: bilinmeyen job 404, `failed` değil 409 `CONFLICT`.

### 2.6 Ayarlar (Settings + sözleşme + docs)
`NL2SQL_JOB_MAX_ATTEMPTS` (3, ≥1), `NL2SQL_JOB_RETRY_BACKOFF_SECONDS` (30, >0), `NL2SQL_JOB_MAX_CONCURRENT` (0, ≥0).

## 4. Out of scope (TECH-DEBT §41)
- Harici broker; çok-host kuyruk.
- Upload (Form) endpoint'inde priority; job yanıtlarında `priority`/`attempts`/`dead_lettered_at` alanları.
- Job başına/kiracı başına kota, adil sıralama (fairness), zamanlanmış (cron) job.
- Frontend'de kuyruk/dead-letter görünümü.
- Dead-letter retention/otomatik temizleme.
