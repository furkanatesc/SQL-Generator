# Sprint 26.9 — Result-Set Privacy & Limits Contract · Design

**Phase 7 (Security & Governance) · Contract-first, no execution · 2026-06-26**

## 1. Purpose

Define a deterministic, no-I/O backend contract that operates on the
**post-execution result set** — the actual rows and column names a query
returned — and produces a single unified result with two distinct concerns:

* **Limits (a GATE):** given a caller-supplied policy (`max_rows` / `max_bytes`
  / `max_columns`), decide whether the result is returned whole (`ALLOW`),
  trimmed to a prefix of rows (`TRUNCATE`), or refused (`DENY`). This bounds
  result size for cost, transport, and denial-of-wallet reasons.
* **Privacy (an advisory SIGNAL):** scan the actual returned cell values for
  PII/PHI using the 26.5 value-format heuristics, and report — **per column** —
  which categories appeared, how many cells matched, and the highest confidence.
  This is **not** a gate; it never changes the limit decision.

This is the **first** Phase 7 contract that inspects **returned data** rather
than SQL or natural language. Where 26.0–26.5 answer questions about a *SQL
statement*, 26.8 inspects *natural language*, and 26.6/26.7 record/orchestrate
governance, 26.9 answers, one layer later — after execution:

* Is this result set too large for policy (and what do we do about it), and does
  the **data that actually came back** contain personal/health information the
  pre-execution layers could not see?

26.5 detects PII/PHI from SQL *identifiers and literals*; it explicitly never
sees rows. 26.9 closes that gap by scanning the real values — a `notes` column
full of emails, a free-text field leaking SSNs — that no static SQL analysis
could surface.

**Core stance — the contract carries and cuts NO data.** It receives the rows,
computes a `kept_rows` *decision*, and returns only that count plus secret-free
summaries. The **caller** applies `rows[:kept_rows]`. The result object never
contains a raw cell value or a sample row. This preserves the house invariants:
no I/O, secret-free results, immutable frozen dataclasses.

## 2. Scope

**In scope:** the contract — limit-disposition / limit-reason-code enums; an
immutable caller-supplied limit policy; an immutable request (`columns`, `rows`,
`policy`); per-column privacy records; a unified immutable result with a
secret-free `to_dict()`; the deterministic limit-gate algorithm; the full-result
PII/PHI value scan reusing 26.5; a shared value-scan helper extracted from 26.5
(`_pii_value_scan.py`); an audit interlock (`AuditCategory.RESULT_SET_PRIVACY` +
`from_result_set` builder); exports from `__init__.py`; exhaustive unit tests.

**Out of scope (later sprints / deliberate):** any actual row slicing or data
transport (the caller applies the `kept_rows` decision); query execution / DB
drivers / adapters (the caller has already executed and passes rows in); column
*truncation* as a size remedy (a column overage is always a DENY — see §7);
masking / redaction / tokenization of detected PII (a remedy, not this detector —
a later sprint); streaming / chunked result handling; a real type system over
cell values (cells are treated as opaque, str-cast for scanning and byte
estimation); locale-specific national IDs beyond 26.5's formats; semantic / ML
classification; credential vault (26.10); policy eval (26.11); any I/O, API/UI
wiring, tenant/RBAC/AuthN.

## 4. Shared value-scan helper (`_pii_value_scan.py`) — refactor of 26.5

26.5's literal-value layer (`_EMAIL_RE`, `_SSN_RE`, `_IBAN_RE`, `_PHONE_RE`,
`_CARD_CANDIDATE_RE`, `_luhn_ok`, `_detect_literal_matches`) already scans a
string for PII/PHI value formats. 26.9 needs exactly this, applied per cell.
**Approach A:** extract the value-format regexes, `_luhn_ok`, and the scan
function into a new shared module `_pii_value_scan.py`, and have **both** 26.5
and 26.9 import from it.

The shared helper exposes a single public function:

```python
def scan_value_categories(text: str) -> List[Tuple[SQLPiiPhiCategory, SQLPiiPhiConfidence]]:
    """Value-format PII/PHI detections over an arbitrary string. Deterministic,
    value-free output: (category, confidence) pairs only. The same logic 26.5
    runs over the raw SQL string, factored out for reuse over result-set cells."""
```

To avoid a circular import, the category/confidence/data-class **enums**
(`SQLPiiPhiCategory`, `SQLPiiPhiConfidence`, `SQLDataClass`) and
`_CATEGORY_DATA_CLASS` move into (or are anchored by) the shared module as the
canonical definition; `sql_pii_phi_detection.py` **re-exports** them so its
existing public API is unchanged. This is **behavior-preserving**: 26.5's
`_detect_literal_matches` becomes a thin wrapper over `scan_value_categories`,
and 26.5's existing tests (which lock its behavior) must stay green untouched.

> **Refactor safety:** the 26.5 refactor is a pure move + re-export. No 26.5
> behavior, output, ordering, or public symbol changes. The existing 26.5 test
> suite is the regression gate — it runs unmodified and must pass.

## 5. Enums

```python
class ResultSetLimitDisposition(str, Enum):   # ordered ALLOW < TRUNCATE < DENY
    ALLOW = "allow"          # returned whole
    TRUNCATE = "truncate"    # return a row prefix (kept_rows < total_rows)
    DENY = "deny"            # refuse the result

class ResultSetLimitReasonCode(str, Enum):
    WITHIN_LIMITS      = "within_limits"        # -> ALLOW
    EMPTY_RESULT       = "empty_result"         # -> ALLOW (0 rows)
    ROW_CAP_TRUNCATED  = "row_cap_truncated"    # -> TRUNCATE (row-bound)
    BYTE_CAP_TRUNCATED = "byte_cap_truncated"   # -> TRUNCATE (byte-bound)
    ROW_CAP_DENIED     = "row_cap_denied"       # -> DENY (overage, truncate not allowed, row-bound)
    BYTE_CAP_DENIED    = "byte_cap_denied"      # -> DENY (overage, truncate not allowed OR single row > max_bytes)
    COLUMN_CAP_DENIED  = "column_cap_denied"    # -> DENY (column count over cap; always, see §7)
```

Privacy **reuses 26.5's** `SQLPiiPhiCategory`, `SQLPiiPhiConfidence`,
`SQLDataClass` (canonically defined in `_pii_value_scan.py` per §4) — no new
privacy enums. A module-level `_LIMIT_DISPOSITION_ORDER` map gives a total order
for deterministic max/severity computation.

## 6. Records (immutable, frozen)

```python
@dataclass(frozen=True)
class ResultSetLimitPolicy:
    """Caller-supplied, frozen limit policy. None on any cap = that dimension is
    unbounded. truncate_allowed governs the row/byte overage remedy (see §7)."""
    max_rows: Optional[int] = None
    max_bytes: Optional[int] = None
    max_columns: Optional[int] = None
    truncate_allowed: bool = False
    def __post_init__(self) -> None: ...   # each cap None or a non-negative int; truncate_allowed a bool

@dataclass(frozen=True)
class ResultSetPrivacyLimitsRequest:
    version: str
    columns: Tuple[str, ...]               # column names, positional
    rows: Tuple[Tuple[Any, ...], ...]      # row-major; each row aligns to columns
    policy: ResultSetLimitPolicy
    def __post_init__(self) -> None: ...   # version match; columns a tuple of str; rows a tuple of tuples; policy type

@dataclass(frozen=True)
class ResultSetColumnPrivacy:
    """Per-column PII/PHI summary. Secret-free: a category + a COUNT, never a value."""
    column_index: int
    column_name: str
    category: SQLPiiPhiCategory
    matched_cell_count: int
    highest_confidence: SQLPiiPhiConfidence
    data_class: SQLDataClass
    def to_dict(self) -> Dict[str, Any]: ...

@dataclass(frozen=True)
class ResultSetPrivacyLimitsResult:
    version: str
    # --- limit gate ---
    limit_disposition: ResultSetLimitDisposition
    limit_reason_code: ResultSetLimitReasonCode
    total_rows: int
    total_columns: int
    estimated_bytes: int
    kept_rows: int                         # DECISION: caller applies rows[:kept_rows]
    truncated: bool                        # True iff limit_disposition == TRUNCATE
    # --- privacy signal ---
    column_privacy: Tuple[ResultSetColumnPrivacy, ...]
    privacy_categories: Tuple[SQLPiiPhiCategory, ...]      # union, sorted, de-duplicated
    highest_privacy_confidence: Optional[SQLPiiPhiConfidence]
    has_phi: bool
    reason: str
    def __post_init__(self) -> None: ...
    def to_dict(self) -> Dict[str, Any]: ...   # JSON-safe; enum .value's; NO raw cell, NO sample row
```

- `kept_rows` is the **only** size lever the result exposes: it is the number of
  leading rows the caller should keep. On `ALLOW` it equals `total_rows`; on
  `DENY` it is `0`; on `TRUNCATE` it is the computed prefix length.
- `column_privacy` reports only columns that had at least one match; a column may
  appear **once per detected category** (e.g. a free-text column matching both
  `EMAIL` and `PHONE` yields two `ResultSetColumnPrivacy` entries).
- The result carries **no data** — no cell value, no sample, no row. Privacy is a
  category + a count + a confidence, per column. This is the secret-free invariant.

## 7. Limit-gate algorithm (order matters)

Given `total_rows = len(rows)`, `total_columns = len(columns)`:

1. **Estimate bytes.** `estimated_bytes = Σ over every cell of
   len(str(cell).encode("utf-8"))`. `None` cells str-cast to `"None"` (a
   deterministic, documented approximation — this is a size estimate, not an
   exact wire size). Column names are **not** counted (data, not header, is the
   size concern).
2. **Column cap FIRST.** If `max_columns is not None and total_columns >
   max_columns` → `DENY`, `COLUMN_CAP_DENIED`, `kept_rows = 0`, **regardless of
   `truncate_allowed`.** *(Approved decision.)* Rationale: truncating columns
   would silently change the result's schema/shape — an unacceptable, invisible
   data loss. A too-wide result is refused, never quietly narrowed.
3. **Empty result.** Else if `total_rows == 0` → `ALLOW`, `EMPTY_RESULT`,
   `kept_rows = 0`, `truncated = False`. (The column cap in step 2 still applied:
   a zero-row result with too many columns is still `COLUMN_CAP_DENIED`.)
4. **Row/byte caps.** Compute the **longest leading-row prefix** that satisfies
   *both* `max_rows` and `max_bytes` (each ignored if `None`). Let
   `kept = prefix_len`, and let the result be **over limit** iff `kept <
   total_rows`.
   - If not over limit → `ALLOW`, `WITHIN_LIMITS`, `kept_rows = total_rows`.
   - Else if `truncate_allowed`:
     - If `kept == 0` (the very first row alone already exceeds `max_bytes`) →
       `DENY`, `BYTE_CAP_DENIED`, `kept_rows = 0` (**fail-closed**: we cannot
       return even one row within the byte budget, and returning a partial row is
       not an option).
     - Else → `TRUNCATE`, `kept_rows = kept`, `truncated = True`. Reason code is
       `BYTE_CAP_TRUNCATED` if the byte cap was the binding constraint (the prefix
       stopped on bytes before it stopped on rows), else `ROW_CAP_TRUNCATED`.
   - Else (`not truncate_allowed`) → `DENY`, `kept_rows = 0`. Reason code is
     `BYTE_CAP_DENIED` if the byte cap was binding, else `ROW_CAP_DENIED`.

"Binding constraint" is determined deterministically: walk rows accumulating
bytes and a row counter; the cap that the prefix hits first (or, on a tie, byte)
is reported as binding. The prefix walk is **independent of and prior to** the
privacy scan (§8) — the two computations do not interact.

## 8. Privacy scan (advisory signal, full result set)

- For each column index `c`, scan **every** cell in that column (the **full**
  result set, not just `rows[:kept_rows]` — PII in rows that truncation would
  drop is still reported; the two concerns are orthogonal). *(Approved: full
  scan, documented.)*
- Per cell: skip `None` and empty/whitespace-only values; otherwise `str(cell)`
  and run `scan_value_categories` (§4).
- Aggregate per `(column, category)`: `matched_cell_count` = number of cells in
  that column that produced that category at least once; `highest_confidence` =
  max confidence seen for that category in that column; `data_class` from
  `_CATEGORY_DATA_CLASS`.
- Emit one `ResultSetColumnPrivacy` per `(column, category)` with ≥1 match,
  ordered deterministically: PHI before PII, then column_index, then category
  value.
- Roll up across all columns: `privacy_categories` = sorted/de-duplicated union;
  `highest_privacy_confidence` = global max (`None` if no matches); `has_phi` =
  any matched category maps to PHI.

> **Performance (documented, accepted):** the scan is `O(rows × cols × regex)` —
> it touches every cell. For very large result sets this is the dominant cost.
> This is accepted for this sprint: the contract is deterministic and exact, and
> the caller controls input size (and can apply the limit gate's `kept_rows`
> before deciding to call, though privacy intentionally scans the full set). An
> optional `privacy_sample_rows` cap is **deferred as YAGNI** — *(approved)* —
> and can be added to the policy later without changing the result shape.

## 9. Evaluation flow

The contract surface is a stateless class
`ResultSetPrivacyLimitsContract` with
`.evaluate(request) -> ResultSetPrivacyLimitsResult` (mirrors the 26.3 / 26.5 /
26.8 class shape).

1. Validate request type & version (mismatch raises
   `ResultSetPrivacyLimitsContractError`). Validate `columns` is a tuple of
   strings, `rows` a tuple of tuples, `policy` a `ResultSetLimitPolicy`
   (structural malformation raises — the caller built the request wrong).
2. Run the limit-gate algorithm (§7) → `limit_disposition`, `limit_reason_code`,
   `kept_rows`, `truncated`, `estimated_bytes`, `total_rows`, `total_columns`.
3. Run the privacy scan (§8) → `column_privacy`, `privacy_categories`,
   `highest_privacy_confidence`, `has_phi`.
4. Compose a human `reason` summarizing both concerns (limit disposition + the
   privacy headline), and build the immutable result.

The limit gate and the privacy scan are **independent** — neither reads the
other's output. A `DENY` result still carries the full privacy summary (so audit
records what was in the data even when it was refused).

## 10. Audit interlock (mirrors 26.6/26.7/26.8)

Extend `backend/app/security/audit_event.py`:

- Add `AuditCategory.RESULT_SET_PRIVACY = "result_set_privacy"`.
- Add `from_result_set(result, *, event_id, occurred_at, actor, resource,
  prev=None)` that normalizes a `ResultSetPrivacyLimitsResult` into one
  immutable, secret-free `AuditEvent`:
  - **outcome:** `DENY` → `DENIED`; otherwise `TRUNCATE` **or** any privacy match
    present → `FLAGGED`; otherwise (`ALLOW`, no privacy match) → `ALLOWED`.
  - **severity:** `max(limit_severity, privacy_severity)` over the
    `_SEVERITY_ORDER` total order, where
    - `limit_severity`: `DENY` → `MEDIUM`, `TRUNCATE` → `LOW`, `ALLOW` → `INFO`.
    - `privacy_severity` (the 26.5 matrix): PHI + HIGH → `CRITICAL`; PHI → `HIGH`;
      PII + HIGH → `MEDIUM`; PII → `LOW`; none → `INFO`.
  - **`sql_sha256 = None`** — 26.9 inspects a result set, not a SQL statement.
  - **`details = result.to_dict()`** — the secret-free summary.
  - `action = "evaluate_result_set"`. Linkable via the existing `link()`
    hash-chain helper.

Import direction is **audit → result_set_privacy_limits** (audit already imports
every other contract; no cycle). Export the new symbols from `__init__.py` and
add to `__all__`.

## 11. Documented limitations (26.5/26.8-style honesty)

- **Heuristic privacy, both directions:** the value scan reuses 26.5's
  regex/Luhn heuristics — it **under-detects** (an unlisted ID format, PHI as
  free prose) and **over-detects** (a non-PII number passing Luhn by chance, an
  order id that looks like a phone). It is a **signal, never proof, never a
  gate.** It informs governance; it does not block.
- **Byte estimate is approximate:** `estimated_bytes` uses `len(str(cell))`
  UTF-8 bytes and does not model the wire/serialization format, per-cell
  overhead, or column headers. It is a deterministic upper-ish approximation for
  policy decisions, not an exact transfer size.
- **`None`/non-string cells:** cells are str-cast for both byte estimation and
  scanning; the contract has no type system and treats values opaquely.
- **Full-set scan cost:** `O(rows × cols × regex)` — see §8. Accepted this
  sprint; `privacy_sample_rows` deferred.
- **Column overage is never trimmed:** a too-wide result is always `DENY`, never
  silently narrowed (§7) — by design, not a limitation to fix.
- **PHI is not detectable post-execution:** the result-set value scan reuses only
  26.5's value-format heuristics, which emit PII categories (email, SSN, IBAN,
  credit card, phone) only; PHI categories (medical record number, diagnosis,
  health-generic) require name/declared-column signals that 26.9 does not have.
  Consequently `has_phi` is effectively always `False` this sprint, and the
  PHI-tier severity escalations and PHI-first ordering exist only for parity with
  the shared 26.5 matrix and future name-aware detection.

## 12. Test matrix

- **Limits — ALLOW:** within all caps → `ALLOW`, `WITHIN_LIMITS`,
  `kept_rows == total_rows`, `truncated False`. Unbounded policy (all `None`) →
  always `ALLOW`.
- **Limits — empty:** 0 rows → `ALLOW`, `EMPTY_RESULT`, `kept_rows == 0`.
- **Limits — row cap:** over `max_rows`, `truncate_allowed True` → `TRUNCATE`,
  `ROW_CAP_TRUNCATED`, `kept_rows == max_rows`; same over-limit with
  `truncate_allowed False` → `DENY`, `ROW_CAP_DENIED`, `kept_rows == 0`.
- **Limits — byte cap:** over `max_bytes` (binding before rows) →
  `BYTE_CAP_TRUNCATED` / `BYTE_CAP_DENIED` per `truncate_allowed`; the prefix
  length satisfies the byte budget.
- **Limits — single oversized row:** `truncate_allowed True` but row 0 alone >
  `max_bytes` → `DENY`, `BYTE_CAP_DENIED`, `kept_rows == 0` (fail-closed).
- **Limits — column cap:** `total_columns > max_columns` → `DENY`,
  `COLUMN_CAP_DENIED`, `kept_rows == 0`, **even when `truncate_allowed True`** and
  **even with 0 rows**.
- **Binding constraint:** a case where bytes bind before rows reports a
  `BYTE_CAP_*` code; rows bind before bytes reports `ROW_CAP_*`.
- **Privacy — detection:** a column of emails → one `ResultSetColumnPrivacy`
  (`EMAIL`, correct `matched_cell_count`, confidence); a free-text column with
  both an email and a phone → two entries. Because the value scan surfaces PII
  categories only (see §11), `has_phi` stays `False`; the PHI ordering and
  severity paths are exercised structurally but never fire on value-scan input.
- **Privacy — full-set scan:** PII present only in rows beyond `kept_rows` (rows
  truncation would drop) is **still reported** — privacy scans the full set.
- **Privacy — skips:** `None` / empty / whitespace cells produce no match;
  non-string cells are str-cast and scanned.
- **Privacy — rollup:** `privacy_categories` sorted/de-duplicated;
  `highest_privacy_confidence` = true max; ordering PHI-before-PII then
  column_index then category.
- **Independence:** a `DENY` (any cause) result still carries the full privacy
  summary.
- **Secret-free:** `to_dict()` JSON-serializable; a known PII value placed in the
  rows is **absent** from the dict (only category + count + confidence present).
  Same assertion for the audit `from_result_set` event.
- **Validation:** version mismatch (request & result) raises; bad `columns` (not
  a tuple / non-str), bad `rows` (not a tuple of tuples), bad `policy` type,
  negative cap → raises.
- **Immutability** (`FrozenInstanceError`) on every frozen record.
- **Audit interlock:** `from_result_set` maps DENY→DENIED, TRUNCATE→FLAGGED,
  privacy-match→FLAGGED, clean ALLOW→ALLOWED; severity = max(limit, privacy);
  `sql_sha256 is None`; hash-chain-linkable; secret-free.
- **26.5 regression:** the full existing 26.5 test suite passes unchanged after
  the `_pii_value_scan.py` extraction; the new `scan_value_categories` has direct
  tests for each value format.
