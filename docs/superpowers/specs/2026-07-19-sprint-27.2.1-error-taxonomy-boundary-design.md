# Sprint 27.2.1 — Error Taxonomy Boundary (design)

**Tarih:** 2026-07-19
**Faz:** 8 (Observability)
**Öncül:** Sprint 27.2 (Error Taxonomy v2, PR #136 merged). 27.2 taksonomiyi tek
registry'de topladı (`backend/app/errors/`, `StrEnum` `ErrorCode`/`ErrorCategory`)
ve `run_pipeline` sonucuna `error_code` ekledi — ama bilinçli olarak pipeline
katmanında durdu. Bu sprint kodu iş/API/frontend sınırından geçirir.

## 1. Amaç

`result["error_code"]` (bir `ErrorCode | None`) pipeline'da üretiliyor ama sınırda
kayboluyor: job'a yazılmıyor, API response'unda yok, frontend'e ulaşmıyor. Ayrıca
frontend'in API hata mesajı okuma yolu, backend'in gerçek hata envelope'uyla
uyumsuz ve sessizce her mesajı düşürüyor. Bu sprint iki şeyi yapar:

1. **error_code end-to-end** — pipeline sonucu → job persist → API response →
   frontend interface. (Plumbing; UI davranışı değişmez.)
2. **`api.ts` `detail` bug fix** — kullanıcı-görünür: RAG/indexing endpoint'lerinde
   gerçek hata mesajını kullanıcıya ulaştır.

## 2. Kapsam

### Kapsam içi
- **#1** error_code end-to-end (backend persist + API + frontend interface).
- **#2** `api.ts` hata mesajı çıkarımı düzeltmesi.

### Kapsam dışı — ERTELENDİ (sessiz düşürme yok)
- **#3 `ExecutionSpanDetail.error_code` beslemesi.** Canlı pipeline SQL'i
  **execute etmiyor** (`live_trace_assembly.py:177`: "EXECUTION — Faz-1'de canlı
  çalıştırma yok (spec §1.4)"); EXECUTION span'i koşulsuz `SKIPPED`. Beslenecek bir
  execution `error_code`'u yok; SKIPPED span için altyapı kurmak YAGNI ihlali olur.
  Bu kalem **canlı execution etkinleştiren faza bağımlıdır**, taksonomi-sınır
  meselesi değildir. TECH-DEBT §4.3 bu bağımlılığı belirtecek şekilde güncellenir.
- TECH-DEBT §4'ün diğer kalemleri (#4 classify_sql_error düzyazı ayrıştırma,
  #5 SQLFailureCategory birleştirme, #6 HTTP code sözlüğü, #7 retryable ekseni,
  #8 details["error_type"] adı, #9 trace DB migrate) bu sprint dışıdır.
- Frontend'de `error_code`'un GÖRÜNÜR kullanımı (yerelleştirilmiş mesaj eşlemesi,
  kod rozeti) kapsam dışı — yalnız interface'te taşınır.

## 3. Tasarım

### 3.1 Backend — error_code persist + API (#1)

**Persistence (`backend/app/database.py`):**
- `jobs` tablosuna `error_code TEXT` kolonu, mevcut idempotent migration deseniyle:
  ```python
  try:
      cursor.execute("ALTER TABLE jobs ADD COLUMN error_code TEXT")
  except sqlite3.OperationalError:
      pass  # Column already exists
  ```
  Eski satırlar `NULL` alır (kabul edilir; geçmiş job'lar kod taşımaz).
- `get_job` değişmez — `SELECT *` + `dict(row)` olduğundan yeni kolon otomatik akar.
- **`update_job_status` — dinamik SET-clause refactor.** Mevcut 4-dallı if/elif
  merdiveni (`result_sql`/`error_message` kombinasyonları) `error_code` eklenince
  kombinatoryal patlar. Bunun yerine non-None alanlardan SET cümlesi dinamik kurulur:
  ```python
  def update_job_status(job_id, status, result_sql=None, error_message=None,
                        error_code=None):
      now = datetime.datetime.utcnow().isoformat()
      fields = ["status = ?"]
      values = [status]
      for col, val in (("result_sql", result_sql),
                       ("error_message", error_message),
                       ("error_code", error_code)):
          if val is not None:
              fields.append(f"{col} = ?")
              values.append(val)
      fields.append("updated_at = ?")
      values.append(now)
      values.append(job_id)
      cursor.execute(f"UPDATE jobs SET {', '.join(fields)} WHERE id = ?", values)
  ```
  **Davranış korunur:** mevcut `update_job_status` testleri DEĞİŞMEDEN geçmeli
  (aynı kolonlar aynı koşullarda yazılır). Kolon adları koddaki sabit whitelist'ten
  gelir (SQL injection yüzeyi yok).

**Job runner (`backend/app/main.py`):**
- Başarısız dal (~satır 397): `error_code`'u geçir. `res.get("error_code")` bir
  `ErrorCode | None`. Açıklık için değer olarak sakla:
  ```python
  ec = res.get("error_code")
  update_job_status(job_id, "failed",
                    error_message=res["error"] or "SQL üretimi başarısız.",
                    error_code=(ec.value if ec is not None else None))
  ```
  (`ErrorCode` StrEnum olduğu için sqlite'a zaten değer bind olurdu; `.value`
  açıklık ve gelecekteki tip değişimine karşı sağlamlık için.)
- `except Exception` dalı (~satır 405): pipeline patladı, `res` yok →
  `error_code` verilmez → `NULL`. Bu, registry'nin **INTERNAL → kod yok**
  tasarımıyla tutarlıdır: beklenmeyen job-runner exception'ının taksonomi kodu
  yoktur. (Yorumla belgelenir.)

**API şeması (`backend/app/api/schemas.py`):**
- `JobDetailResponse`'a `error_code: Optional[str] = None` alanı. Endpoint yanıtı
  job dict'ten kurulduğu için alan otomatik dolar (job dict `error_code` taşır).

### 3.2 Frontend — interface alanı (#1) + hata mesajı fix (#2)

**Interface (`frontend/src/services/api.ts`):**
- JobDetail tipine `error_code: string | null` eklenir. UI'da GÖRÜNMEZ — yalnız
  taşınır (gelecekteki tüketiciler / devtools).

**Hata mesajı çıkarımı (#2):**
- Backend'in TÜM hataları global handler'larla `{"error":{"code","message",
  "details"}}` envelope'una sarıyor (`api/errors.py` — HTTPException dahil).
  Frontend ise `errData.detail` okuyor (`api.ts:161,174,187`) → `detail` hiçbir
  zaman yok → her mesaj sessizce düşüyor, kullanıcı hardcoded fallback görüyor.
- **Saf helper çıkar** (`frontend/src/utils/apiError.ts`), test edilebilir + DRY:
  ```typescript
  // Backend hata envelope'undan mesaj çıkarır: {"error":{"message":...}}.
  // Eski/beklenmedik şekillere karşı dayanıklı; hiçbiri yoksa fallback döner.
  export function extractApiErrorMessage(errData: unknown, fallback: string): string {
    if (errData && typeof errData === 'object') {
      const err = (errData as any).error;
      if (err && typeof err.message === 'string' && err.message) return err.message;
      // FastAPI default {"detail": "..."} biçimine geriye dönük tolerans:
      const detail = (errData as any).detail;
      if (typeof detail === 'string' && detail) return detail;
    }
    return fallback;
  }
  ```
- Üç çağrı noktası (RAG search, business-rule index, SQL-history index)
  `errData.detail || '<fallback>'` yerine `extractApiErrorMessage(errData, '<fallback>')`
  kullanır. Sonuç: gerçek backend mesajı artık kullanıcıya ulaşır.

## 4. Test stratejisi

**Backend (pytest):**
- Job API contract testi genişletilir: **başarısız bir job'ın `error_code`'u
  persist edilir ve response'ta döner** (örn. bir `syntax_error` senaryosu →
  job detail `error_code == "syntax_error"`).
- `update_job_status` unit testi: yeni `error_code` param yazılır; **mevcut
  kombinasyonlar (yalnız status / +result_sql / +error_message) aynen çalışır**
  (dinamik refactor davranış-koruma kanıtı).
- Migration idempotency: `init_db` iki kez çağrılınca `error_code` kolonu bir kez
  eklenir, hata vermez.
- `except Exception` dalı: beklenmeyen exception'da job `error_code` `NULL` kalır.

**Frontend (node-script, mevcut `graphSelection.test.ts` kalıbı):**
- `frontend/tests/apiError.test.ts` — `extractApiErrorMessage` için, `node
  --experimental-strip-types` ile koşar. Vakalar: envelope `{"error":{"message"}}`
  → mesaj; `{"detail":"..."}` → geriye dönük mesaj; `{}` / null / bozuk → fallback.
- ⚠️ Frontend'de tam test framework (vitest) YOK — bu tek-dosya script deseni
  bilinçli geçici çözümdür (TECH-DEBT §2). Interface tip değişikliği `tsc` ile
  doğrulanır. Vitest kurulumu ayrı bir kalemdir, bu sprint dışı.

## 6. Başarı ölçütleri

1. Bir SQL üretim job'ı taksonomik bir hatayla (örn. `syntax_error`) başarısız
   olduğunda: `GET /api/jobs/{id}` yanıtı `error_code` alanını taşır ve pipeline'ın
   ürettiği koda eşittir.
2. `error_code` job DB'sinde persist edilir; `error_message` ile birlikte yazılır.
3. Beklenmeyen (INTERNAL) job-runner exception'ı `error_code = NULL` bırakır.
4. `update_job_status`'un mevcut testleri değişmeden geçer (davranış korunur).
5. RAG search / business-rule / SQL-history endpoint'leri hata verdiğinde frontend
   backend'in gerçek mesajını gösterir (fallback değil).
6. `extractApiErrorMessage` node-script testi yeşil; full backend suite 0 failed.

## 7. Bağımlılık yönü / mimari notlar

- Değişiklik yönü tek yönlü ve mevcut katmanlara uyumlu: `database.py` (persist) ←
  `main.py` (job runner) ← `schemas.py` (API) ← `api.ts` (frontend). `app.errors`
  saf yaprak katmanı DEĞİŞMEZ.
- `error_code` sınırda **string** olarak taşınır (`ErrorCode.value`); frontend ham
  string alır. Bu bilinçli — API sözleşmesi tipsiz string kod taşır, enum değil.
